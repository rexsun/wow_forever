# Anchoring.lua

Positions component frames using `anchor_parent`/`anchor_side`/`anchor_offset_x`/`anchor_offset_y`/`anchor_width_pct`/`anchor_width_mode`. Free-moving components use raw `SetPoint` fields (do not call `SetWidth`/`SetHeight` — components manage own dimensions). Uses `safeClearAllPoints`/`safeSetPoint` wrappers (base C methods) to avoid taint. Skips layout during combat.

## Recursive layout

A static anchor tree (`anchorRoots` + `anchorChildren`) is built once and invalidated only on config changes (`RebuildAnchorTree`). Layout is applied via a single recursive function (`layoutRecursive`) that traverses the tree top-down, passing parent alpha, fade, rootVisible, and anchorFrame as parameters — no per-pass table allocation (`deferredRoots` scratch reused across calls). Results are stored in `lastResult` (overwritten in-place) for external queries.

**`position_reference` followers** (the secure-click trackers) are roots laid out in a second pass, placed at their reference's screen rect with one point on `UIParent`. Every pass re-anchors each follower, and a re-anchored frame reads back its old rect for the rest of that frame. So a follower of a follower (RaidBuffTracker follows ConsumableBuffTracker by default) does not measure it. The pass records the anchor it set (`placedThisPass`, `lastResult[name].placedPoint/X/Y`) and the next follower rebuilds the rect from that anchor plus the size the reference's own layout set, `GetComponentSize()`, read at that moment so a resize by the reference's `ContentLayout` counts. Both secure-click trackers report their last `applyLayout` size there (`layoutW`/`layoutH`), not `container:GetSize()`: the frame's size reads back stale in that frame too. Before 2026-09-23 it measured, and after combat, when the frozen ConsumableBuffTracker moved, RaidBuffTracker landed where it had been until the next full pass (user report: offset after combat, right after a click). A first fix took the size from `GetSize()` and put RaidBuffTracker on ConsumableBuffTracker's top edge (second report). A follower of an ordinary component still measures it. That component is re-anchored too, but it followed its parent live through the fight, so the pass puts it back where it already was and the old rect still matches. The follower is still off by a pass when the same pass resizes that component. Pinned by `tests/followerchain_check.lua`.

## Dirty-loop re-entrancy

A re-entrancy guard (`isRefreshing`) prevents Show/Hide hooks from nesting into a recursive layout during a pass. When an in-flight pass calls `Show()/Hide()` on component frames, visibility hooks fire `OnComponentStateChange`, which sets `needsStateChange = true`. `applyLayout`'s outer `repeat..until` loop then re-runs the pass in the same call stack — no timer defer, no one-frame stutter — capped at `MAX_APPLY_PASSES` (3) to prevent infinite loops. Outside a pass, `OnComponentStateChange` calls `anchor.Refresh` synchronously.

## Resize-driven child relayout

When a tracker container's content size changes (icon add/remove, hide-when-ready count, collapse), its *anchored children* must re-resolve against the new parent rect. The `setTargetSize` helper in `LayoutViewerBars` (and the equivalent chokepoint in `Core/IconTracker.lua`) fires this **only when the resized component actually has anchored dependents** (`HasAnchoredDependents(name)` — `anchorChildren[name]` non-empty); most setups anchor nothing to a tracker, so it skips entirely.

When there ARE dependents it calls **`RelayoutSubtree(name)`** — a **synchronous, same-frame** scoped equivalent of `applyLayout`'s normal-root branch restricted to `name`'s subtree, **not** a full `anchor.Refresh`. A full relayout of every component per resize spiked combat CPU/GC (see `.context/performance.md`); the subtree pass touches only `name`'s dependents. It reuses `applyLayout`'s exact per-pass prologue (the four cache wipes + `cachedIsMounted`/`cachedInCombat`/`cachedHasTarget`), so `layoutRecursive` is taint-equivalent to a full pass — `RefreshVisibilityOnly` uses the same pattern. `name` is marked visited (its geometry was just set); children read `lastResult[name]` for their inherited context (`anchorFrame`/`alpha`/`fade`/`rootVisible`). A dirty flag raised mid-pass by a genuine Show/Hide side effect escalates to one full `OnComponentStateChange` (rare). Guards: `isInBulkRefresh` (defer to `EndBulkRefresh`), `isRefreshing` (**return without dirtying** — a pass is already walking this subtree top-down and re-lays-out the descendant against its new size, since `ContentLayout` runs before child recursion; setting `needsStateChange` here would wrongly escalate a full Refresh on every combat content-size change, the ~50% CPU regression in `.context/performance.md`), and `pr.anchorFrame == nil` (unpositioned — skip). A `nil` component name can't be scoped, so it falls back to a full `OnComponentStateChange`. Protected containers in combat skip the trigger; the `OnLeaveCombat` refresh catches up.

> **Invariant:** `lastResult[name].rootVisible` must equal what `name` passes its children. The visible-promotion path (component mode-visible under a hidden root) writes it (`if not effectiveOverride`), otherwise `RelayoutSubtree` would inherit a stale `false` and cascade-hide the subtree — the same failure `IsAnchorChainVisible` would report. Every hide path and every forceVisible-rescue path writes it too, always `false`: **a component that is not drawing its own normal content passes `false` to its children, root or not.**

**Reposition-only subtree passes.** A `RelayoutSubtree` fires because `name` *resized*, so its dependents need re-derived sizes and re-flowed icons against the new parent geometry — never a restyle. The module-level `subtreeRepositionOnly` flag is raised around the dependent loop and read at every `component.ContentLayout(not subtreeRepositionOnly)` call site, so the icon trackers (`CooldownTracker`/`UtilitiesTracker`/`BuffTracker`, whose `ContentLayout` **is** their `applyLayout(skinDirty)`) take the **reposition-only fast path** — already-skinned icons skip `ApplyIconBorder` (borders are corner-anchored so they track the resize for free), while all position/size/texcoord work still runs and never-skinned icons still get a first-time skin. Components whose `ContentLayout` takes no argument ignore the bool. The flag is cleared **before** the `if dirty then OnComponentStateChange()` escalation, so an escalated full Refresh skins normally. Before this, every in-combat content-size change ran a full skin pass on every dependent — `UtilitiesTracker.ContentLayout` at ~1.8 ms inside each `RelayoutSubtree`, the dominant cost of the recurring ~5 ms combat frames.

## forceVisible is a hide-bypass, not a visibility source

`GetForceVisible()` is consulted at **hide gates only** — mode (~L1148), rules (~L1190), inherit-chain (~L1359), absent-parent (~L1391) — always in the shape `if not <wouldShow> and not forceVisible then Hide()`. It can therefore only ever **prevent** a hide, never cause one. **Corollary: when nothing would hide a component, flipping its forceVisible cannot change the layout outcome, and firing a refresh for it is pure waste.**

**It is also transparent to children.** A component kept up only by forceVisible does *not* promote `rootVisible = true` down the chain: the mode block's promotion is split, and the `modeVisible == false` arm mirrors the hide branch (`childRootVisible = false`, written through to `lastResult`) instead. Its own frame still draws — that is the whole point of the override — but the subtree resolves as if it had hidden, exactly as a programmatic `GetVisibilityOverride` (Vigor) already did. Without this, forceVisible *granted* visibility rather than merely preventing a hide, contradicting the heading.

The live case: `CooldownTracker` on `visibility = "auto"` (plus a `mounted = "hide"` rule) goes `modeVisible = false` while dragonriding, but `getForceVisible` is true because `overrideMode` is drawing the skyriding ability bar. Every `inherit` descendant — the whole default chain of `SecondaryResources` → `PlayerHealthBar` → `PrimaryResources` → `PlayerCastBar` → `GlobalCooldown` → `UtilitiesTracker`, plus any AF anchored into it — used to keep drawing its normal content beside that bar. A descendant with its **own** forceVisible (SecondaryResources' skyriding Vigor) still shows itself, because that is resolved at its own inherit gate.

> **The two gaps this split shipped with are closed.** The zeroing was guarded by `if not parentFrame`, so it reached only a **root** — a non-root forceVisible component (`PlayerCastBar` defaults to `anchor_parent = "PrimaryResources"`) kept whatever `childRootVisible` it inherited, and the ordinary hide branch had the identical limitation for *any* non-root. All three sites in the mode block now break the chain unconditionally. Note that `parentFrame` was never even a reliable test for "is a root": an externally-anchored root (`private.externalAnchors`) is dispatched with a non-nil `pFrame`, so it fell on the wrong side of the guard too.
>
> The **rules** gate needed its own arm rather than the same edit, because the mode block's promotion runs *before* it and cannot know a rule will fire: `elseif not rulesVisible then` downgrades `childRootVisible` — and `lastResult` — back to `false` when a rule would have hidden the frame and forceVisible saved it.

`anchor.ForceVisibleMatters(name)` encodes exactly that. It returns false only when every gate is provably inert: no programmatic `GetVisibilityOverride`, no `hasAnyHideRule`, and `visibility` is `"inherit"` or `"always"` (any other mode can hide).

Under `"inherit"` the chain gates are resolved **against live state, not settings shape** — having an `anchor_parent` is not the same as being hidden by it. The two chain gates read exactly two facts, so the helper reads the same two: L1359 fires only when the `rootVisible` the parent *passes* is false (that value is `lastResult[parent].rootVisible`), and L1391 only when the parent resolves no frame (`lastResult[parent].anchorFrame == nil`). If the parent currently resolves a frame **and** passes `rootVisible = true`, neither gate can fire and forceVisible is inert *right now* → false. This cannot go stale in a way that drops a needed refresh: any change to the chain's visibility is itself applied by a layout pass, which rewrites `lastResult` before the next call. A component with no `anchor_parent` and no `position_reference` always receives `rootVisible = true`, so it can never be chain-hidden. `position_reference` roots are left conservative (their deferred-root pass treats a nil result as *visible*, inverting the check) — rare enough not to be worth mirroring.

It is deliberately conservative everywhere else: `true` whenever undecidable, so a mis-classification costs a redundant refresh rather than a stuck-hidden frame.

> **Why the live check matters:** the settings-shape-only version returned `true` for any chained `"inherit"` component — which is the common layout (an in-game log showed `PlayerCastBar` → `anchor_parent PrimaryResources`, so the gate never fired and the cast bar kept refreshing ~1/sec). Almost every component is chained; almost none of them are actually hidden.

Callers whose forceVisible flips at high frequency **must** gate on it. `PlayerCastBar.show_when_casting` flips it on every cast start/end (four sites: `restoreCastBar`, `startInstantCastBar`, the `OnCastStart` hook, the `OnHide` hook). On the default profile shape — root, `visibility = "inherit"`, no hide rules — that fired a full-addon `anchor.Refresh` **per GCD at ~17 ms (up to 38/session)** that changed nothing: an in-game watcher confirmed the container's `IsShown` and alpha identical across the flip (alpha tracks the combat fade rule, not casting). The feature still works where it's meaningful — e.g. `hide out of combat` + `show_when_casting`, where a rule genuinely hides the bar and forceVisible overrides it — because that profile makes `ForceVisibleMatters` return true.

## Bulk refresh gate

`BeginBulkRefresh`/`EndBulkRefresh` (called by profile apply) defer `OnComponentStateChange`-triggered refreshes to a single final `anchor.Refresh` at the end of the bulk operation via `pendingBulkStateChange`. Mid-operation re-entrancy during the final refresh still goes through the dirty loop.

`ClearAllComponentPoints` (profile-apply path only — `FullLayoutRefresh`, `OnProfileChanged`, the segment refreshes, the import paths, and login) breaks stale anchor relationships before a restructured tree is laid out. It skips secure/protected frames during combat using the same `secureComponents[name] or frame:IsProtected()` gate as `layoutRecursive` (the freeze gate — distinct from `secureClickComponents`, which has the same two members but is what the anchoring panels and the cross-chain filter branch on) — `ClearAllPoints` is blocked on them. Skipping is safe because `layoutRecursive` re-clears each frame before positioning it, and `ProfileManager`'s deferred `OnLeaveCombat` `FullLayoutRefresh` re-runs the whole pass out of combat.

## Recovery and special tables

Direct-`Refresh` listeners on `EDIT_MODE_LAYOUTS_UPDATED` and `EditMode.Exit` recover from `ApplySystemAnchor`. `nonAnchorableComponents` table marks components (BuffTracker, BuffTrackerBars) that ARE positioned but whose children skip past them in the anchor chain. Four-layer visibility detection on root frames. Content-width mode also activates for components with vertical `layout_direction`.

## Visibility

Per-component `visibility` mode (`"inherit"`, `"always"`, `"auto"`) overrides anchor chain visibility — non-inherit modes fully replace the parent chain check. `"auto"` resolves to **CDM available *and not mounted*** — uniform for primary trackers and AFs, so it mirrors a CDM tracker's mounted-hide (an `auto` AF sourcing a tracker hides in flight just as the tracker's own `mounted="hide"` would). `forceVisible` is still checked first, so an override/skyriding ability bar (`CooldownTracker` `overrideMode`) keeps showing while its normal content — and any `auto` AF sourcing it — hides.

## The combat freeze covers the SecureActionButton trackers only

`secureComponents` is `ConsumableBuffTracker` and `RaidBuffTracker`, whose buttons really are secure. `layoutRecursive` skips them in combat, and so does anything `IsProtected()` reports as protected.

The three AuraContainer trackers — BuffTracker, BuffTrackerBars, OutboundBuffTracker — were members until 2026-09-28, on the premise that an AuraContainer makes its component frame protected. It does not. Their component frame is a plain wrapper around the containers. In combat with an aura shown, `CUE_BT_Container:IsProtected()` read `false false`, and a `Hide()`/`Show()` pair went through. `CUE_BTB_Container`, `CUE_OutboundBuffTracker` and every aura-type Additional Frame's `CUE_AF_*` frame read false too, so the freeze's `IsProtected()` check does not catch an AF either. They are now laid out, shown and hidden in combat like any other component, and their own `Refresh` hides with `Hide()` rather than parking the wrapper at alpha 0.

The freeze had cost them their visibility for whole fights. A wrapper `Hide()`n out of combat could not be shown again until combat ended, because the freeze returns before any visibility code and the trackers' `Refresh` returns under `InCombatLockdown()`. A hidden AuraContainer also registers no `UNIT_AURA` (Blizzard's `ShouldRegisterForDynamicEvents` is `IsVisible() and IsEnabled()`), so it draws nothing at all.

Live case: BuffTracker on "Inherit" under a mount-hidden CooldownTracker. Attacking straight off the mount left it empty for the whole fight: the dismount pass lands in the lockdown, and the frame read `IsShown() false, GetAlpha() 1` mid-fight. `tests/hidefreeze_check.lua` pins it.

No tracker's visibility follows Blizzard's CDM Visible Setting. The clamp that did (in `layoutRecursive`, via `Util.GetViewerVisibleSetting`) was removed in May 2026 (`e7c571d`); `pm.MigrateCDMVisibility` copied an "In Combat Only" viewer into the tracker's own `out_of_combat = "hide"` once, and is that function's only reader. There is no AF-only override of that any more: the `HasNonInheritFrames` path re-`Show()`d a Blizzard-hidden viewer at alpha 0 so "always"-visible AF children stayed renderable, which ran Blizzard's `OnShow → RefreshLayout → RefreshData` cascade from addon code and tainted the CDM's item data (`.context/patterns-cooldownviewer.md` "Viewer Show/Hide"). `manager.HasNonInheritFrames` is gone with its call sites. AF children now follow the viewer down, and `CDMDataSource.IsDataAvailable()` is the signal for consumers that would misbehave rather than degrade.

**Visibility rules** (`visibility_rules` profile field) provide additive conditions: `mounted`, `out_of_combat`, `no_target` — each set to `"hide"` (OR logic: any active condition hides), `"fade"` (AND logic: all configured conditions must be met), or `false` (off). Fade opacity controlled by `fade_alpha` (10–90%). `InvalidateTargetRuleCache` scans them into three flags that pick the combat-entry and target-change passes, and skips a component whose mode is `"hidden"`: the mode gate hides it before the rules are read, and `forceVisible` shows it past both gates, so its rules cannot change what it shows and counting them only bought a full pass on every pull. Every visibility-mode setter (Options, Additional Frame panel, Edit Mode) rescans. Target-change refresh is gated by `anyComponentUsesTargetRule` to skip when no component uses the `no_target` rule, and runs only when `UnitExists("target")` differs from `appliedHasTarget` — the value the last whole-tree pass (`applyLayout` or `RefreshVisibilityOnly`, never the one-subtree `RelayoutSubtree`) evaluated — because `PLAYER_TARGET_CHANGED` also fires on every switch from one target to another, which no rule can see. When that walk `Show()`s or `Hide()`s a component, it schedules a deferred full pass **without** fonts (`scheduleDeferredBulkRefresh()`, not `OnComponentStateChange`, which asks for them): under a `no_target` hide rule that is every target gained or lost, and a font pass restyles every aura button of every tracker.

**Combat transitions.** Both ride the `PLAYER_REGEN_*` pair (`OnEnterCombat` / `OnLeaveCombat`), because every combat read in a pass is `InCombatLockdown()`, which is still false inside `PLAYER_REGEN_DISABLED`; each pass is deferred a frame so it runs on the right side of the lockdown. `InvalidateTargetRuleCache`'s scan (components and Additional Frames) sorts the profile's combat dependence, and the pull runs only what it needs:

| profile has | pull runs |
|---|---|
| an `out_of_combat = "hide"` rule, or the legacy `"only_in_combat"` mode (`anyComponentHidesOutOfCombat`) | the full pass (no font pass) |
| only `out_of_combat = "fade"` rules (`anyComponentFadesOutOfCombat`) | `RefreshVisibilityOnly` |
| neither | nothing — no pass computes anything else that changes at the pull |

A fade changes alpha only, which is all the visibility-only walk writes. A hide reveals frames, and `"only_in_combat"` needs the full pass even though a rule-hide would escalate on its own: the visibility-only walk hides a mode-hidden frame but never `Show()`s one its mode revealed. For the walk to be the whole pass, it re-alphas every enabled component with a `SyncAlpha` — the icon and aura trackers, `OutboundBuffTracker`, every Additional Frame (the AF component forwards to its tracker) — since their icons ignore container alpha or their frame is frozen in combat; `position_reference` roots are re-synced even when disabled, because a mid-fight disable cannot `Hide()` them. A full pass run in combat (the hide-rule pull) ends with the same re-sync, `syncAllComponentAlpha`: the combat freeze returns before `ContentLayout`, which is where the full pass otherwise re-alphas them. Combat exit always runs the full pass: the secure components were frozen for the fight, and it is every **shown** `ContentLayout = Refresh` tracker's catch-up. It skips `ContentLayout` for a hidden one, so the aura trackers and `OutboundBuffTracker` register their own one-shot `OnLeaveCombat` refresh when a data change lands mid-fight (`Core/AuraTrackers.md` "Callback lifecycle").

**Which deferred passes raise `fontsDirty`** (`scheduleDeferredBulkRefresh(withFonts)`, OR-ed across callers in one frame): only a component state change (new text from a rebuild). A pass that merely **reveals** a component — the hide-rule pull, mount/dismount, `RefreshVisibilityOnly`'s escalation — does not: the flag is global, so raising it to reach one hidden component restyled every aura button of every tracker (365 ms per target swap under a `no_target` hide rule, `.context/performance.md`). Every component that returns before its font block keeps the edit itself instead. Trinket, Racial, Consumable and every Additional Frame style only while shown and keep it on a `fontsOwed` latch (the Additional Frame per instance, raising the flag around its hosted tracker's next shown layout); `IconTracker` latches it across its takeover and disabled returns (CooldownTracker's skyriding bar ends on dismount). Combat exit runs without it too; that font pass restyled every aura button on each combat end. The trackers that skip styling *in* combat keep a mid-fight edit themselves: the aura trackers and `OutboundBuffTracker` put it on their persistent AuraContainer restyle flag (`MarkDirty` in the combat early-return), the two secure-click trackers on a `fontsOwed` latch that their next drawing `Refresh` consumes.

**Per-pass game-state cache.** `cachedIsMounted` / `cachedInCombat` / `cachedHasTarget` are seeded at the top of `applyLayout`, `RefreshVisibilityOnly` and `RelayoutSubtree`, cleared at the end, and read **only** through `passIsMounted()` / `passInCombat()` / `passHasTarget()` (`anchor.IsMounted` is `passIsMounted`). Outside a pass the cache is nil and each accessor falls through to the live query. Two rules keep it working, both learned from it being broken:

- The declarations must sit **above their first reader** (they are at the top of the file, right after `isMountedConditionActive`). Lua 5.1 binds an upvalue at closure-definition time, so a reader compiled above the declaration captures the *global* of that name — always nil — and the cache silently never applies. Until 2026-08-23 `evaluateVisibilityRules` sat above the declaration site and paid three live API calls per component per pass while `evaluateVisibilityMode` and `layoutRecursive`, below it, used the cache. Nothing crashed; the optimization just wasn't there. A second declaration further down would reintroduce it by shadowing, so there is exactly one.
- Read them with an explicit `== nil` test, never `cached ~= nil and cached or live()`. That idiom returns the fallback whenever the cached value is **false** — the common case for all three — so it cached only the rarer answer.

The raw `cachedInCombat` truthiness reads inside `layoutRecursive` are deliberate and are *not* accessor calls: that function only ever runs inside a seeded pass, and there nil-means-false is the intended reading.

## Alpha

Per-component `alpha` (0.1–1.0) controls opacity. In "inherit" mode, children use their parent's alpha; in other modes (always, auto, etc.) components use their own alpha. `GetEffectiveAlpha` returns the resolved value (or fade when a visibility rule is active). Returns 1.0 in Edit Mode so components are fully visible for editing.

## Frame strata

Per-component `frame_strata` (saved as `nil` = "inherit", or one of `BACKGROUND`/`LOW`/`MEDIUM`/`HIGH`/`DIALOG`/`FULLSCREEN`/`FULLSCREEN_DIALOG`/`TOOLTIP`) controls which draw layer the component sits on. `resolveEffectiveStrata` walks the `anchor_parent` chain until an explicit setting is found, falling back to `MEDIUM` at free-moving roots. The resolved value is cached in `lastResult[name].effectiveStrata`. Applied during layout inside the existing `not InCombatLockdown()` guard; combat-time changes take effect on the next out-of-combat `Refresh`.
