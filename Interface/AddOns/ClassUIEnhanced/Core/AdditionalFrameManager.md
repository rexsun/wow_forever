# AdditionalFrameManager.lua

Creates and manages user-defined additional frames that route specific spells out of the CDM-fed trackers into independent, positionable frames.

Three types, each rendering through **its own factory tracker** — no type reads live CooldownViewer children any more:
- **"spells"** — cooldown icon grid. Owns an `IconTracker`, the same factory CooldownTracker and UtilitiesTracker run on.
- **"buffs"** — icon grid, aura-driven. Owns an `AuraIconTracker`.
- **"bar"** — bar stack, aura-driven. Owns an `AuraBarTracker`.

The migrated primary trackers likewise render their own buttons (AuraContainer / plain-frame icon pools) and exclude routed spells from their spell maps instead of filtering viewer children. The pre-migration renderer that cross-parented live CooldownViewer children into an AF container (`applyIconLayout`) and its keybind half (`applyKeybindTextForAdditionalFrame`) have been **deleted**: `migrateAdditionalFrames` converts the only other `frame_type` (`"icon"`) to `"spells"` at load, so no frame type ever reached them, and the old code was removed once the factory-backed path was verified in play.

All support horizontal or vertical layout direction with configurable alignment. Each frame registers as a full component with its own container, EditMode entry, and profile settings.

**The `createDefault*Settings` templates are the frames' defaults.** `manager.GetDefaultSettings(frameType)` returns a fresh one with no id or name, and Edit Mode's two reset buttons restore from it (`Core/UI/README.md`). A key that exists only through a `migrateAdditionalFrames` backfill therefore has no default for the reset. The one such key today, `spells`' `no_cd_overlay`, is not shown in Edit Mode, so nothing is lost; a new key belongs in the template as well as the backfill.

**Dual routing model:** a spell can be routed to both a spells AF (ability domain) AND one of buffs/bar AF (buff domain) simultaneously. Within each domain, exclusivity holds (one AF per spell). Parent components exclude routed spells from their spell maps (`CDMDataSource.BuildComponentSpellMaps` consults `IsSpellRouted` per domain). `IsSpellRouted` and `GetRoutedFrameSettings` resolve through the same `Util.ResolveByBaseOrOverride` walk over one lookup (`routingTableGet`), so a spell reported as routed always has settings. That walk is base ↔ override only, never from a tracker's key out to its linked ids, so an entry saved under a **linked** id (a cooldown entry's aura, a talent variant's member) needs its owner routed explicitly: `rebuildSpellRouting` adds the entry's key (`linkedOwner`, `CDMDataSource.GetIdentityOwner`), and `buildAFIconSpellMap` / `buildAFOrderRank` draw and rank the entry under that key too, as `buildAFAuraSpellMap` always did — the frame draws the entry, its tracker no longer does. A rank of a **whole spell-rank family** (WoW Forever; `CDMDataSource.GetFamilyRep`, per the frame's bucket) is treated as its family's representative the same way, checked first: the frame holds the whole spell, and `IsCooldownSpellTracked(rep)` is true while any rank is. An id that is itself some entry's own spell is never treated as linked (`CDMDataSource.IsEntryKey`): the owner map keeps one writer per id, and Mass Entanglement `102359` is both a Utility entry and a linked id of Entangling Roots `339`, so without the check a frame holding it drew a cooldown-less Entangling Roots while Mass Entanglement was routed out of its tracker. The owner is known only once the CDM model exists, and it can move when the model is rebuilt. The first rebuilds run at component enable, before the model; on `OnCDMSpellsChanged` the trackers rebuild the model and query routing before this file's own handler runs. So `routingStamp` records which model build a rebuild saw (`CDMDataSource.GetModelStamp`), and both queries call `ensureRoutingResolved` first, which rebuilds on a mismatch; the `OnCDMSpellsChanged` handler rebuilds as well. Layout updates are dispatched via the `OnCDMSpellsChanged` callback — the suppressed viewers' own `Layout()` never fires.

**`assigned_spells` is edited in the Options Tracking tab**, the only editor of it
(`Core/TrackingModel.md`): Move to a frame writes a CDM entry's row key, **Add item...** on a
`spells` frame appends an `{id, source}` addon-source entry (`TrackingModel.AddAddonSource`),
Remove takes one entry out, and Up/Down reorders — each ending in `OnSpellAssignmentChanged`.
The Additional Frames tab's own assigned-spell list and picker are gone; its **Edit spells in the
Tracking tab** button opens that frame's section. This module exposes no assignment writer of
its own and needed none: every writer is a plain list edit followed by that notify.

**Per-child alpha is gone.** No frame type cross-parents a live CooldownViewer child any more — aura types never did, and `spells` draws an `IconTracker`'s own pooled buttons — so the per-viewer alpha-write pass (`applyPerChildAlpha`), its dirty-tracking (`recomputePerChildAlpha`), and the `anchor.Refresh` post-pass that drove it (`Core/Anchoring.md`) were deleted along with the old renderer. The four CDM viewers stay alpha-clamped to 0 by `CDMDataSource`'s unconditional suppression; nothing needs to un-suppress a child any more because nothing draws through one.

> `CDMDataSource`'s `cooldownViewerEnabled` predicate (`needsViewerChildren`) asks a **different** question — *"does something read aura state off a child?"* — and its answer is now **no**, for every AF and every component alike. It used to, indirectly, whenever its `hide_active_swipe` was off or its `icon_visibility_mode` was 2/3, because its hosted `IconTracker` called `CDMDataSource.GetAuraState`. Both routes are gone — the aura takeover became an engine-shown slot button, and the "buffing ≠ ready" term was dropped — so no AF setting can turn Blizzard's Cooldown Manager on — only the profile-level `cdm_target_sounds` option can, for Blizzard's own alerts. See `Core/CDMDataSource.md` "CVar ownership".

## Aura frames (bar / buffs)

`AURA_TRACKER_BY_TYPE` maps the two aura frame types to a factory + source viewer key (`bar` → `AuraBarTracker`/`BuffBar`, `buffs` → `AuraIconTracker`/`BuffIcon`); `"spells"` is deliberately absent, because those route *cooldown* icons, have no aura groups to choose between, and need no viewer key. `getAuraTracker` builds the tracker lazily on first layout and caches it on `instance.auraTracker`; `applyFilteredLayout` dispatches to `applyAuraLayout` (tracker `Refresh`) whenever the type is in that table. `GetComponentSize` / `GetWantsContentWidth` delegate to the tracker.

The tracker is **hosted**: it fills `instance.container`, which the AF already owns and the anchor system already positions, so no competing top-level frame is created. It shares the AF's component name, so its Anchor visibility/alpha queries resolve to this frame's own settings, and its spell map comes from `buildAFAuraSpellMap` (this frame's `assigned_spells`, widened across each entry's aura identity set, plus `CustomSpells.GetSpellMapFor`).

Per-frame settings that only exist on this path:

| Key | Effect |
|-----|--------|
| `always_show_tracked` | The slots (always-show) engine; off is groups — where the button-to-aura binding is secret and **every per-spell feature is inert**. Default `false`. Backfilled onto pre-existing frames by `migrateAdditionalFrames`; turned on once, for `buffs`/`bar` frames, by `pm.MigrateHideWhenInactive` when the player's Blizzard viewer had "Hide when inactive" off. |
| `desaturate_inactive` | Slots only: grey the icon while its aura is not up (or there is no target to hold it). Default `false`; not backfilled — nil reads as off. See `Core/AuraTrackers.md` "Desaturated inactive icons". |
| `aura_unit` | Per-spell unit scope, `"player"` / `"target"`; absent = `"both"`. Set by the Tracking tab's **Track On** column, keyed on the row's key (older entries: the id the user picked); the tracker expands each entry across its aura identity set so linked ids inherit the scope. |
| `proc_glow_*` | `bar` frames only gained these on 2026-08-18 (`style` / `color` / `alpha` / `thickness`); `buffs` always had them. Both Options builders gate the whole proc-glow widget group on `proc_glow_style ~= nil`, so seeding the key in `createDefaultBarSettings` (plus a `migrateAdditionalFrames` backfill for existing bar AFs) is what reveals it — no Options change was needed. Default style is `"border"` on bars, `"blizzard"` on icons: the proc atlas is square art stretched to the host rect. Slots-only, like `active_glow`. |

**The Features column is shared with `spells` frames and must be gated.** Both types fall into the same non-`bar` branch of the Options AF builder, so a `buffs` frame was being offered the whole cooldown-icon feature family while `AuraIconTracker` reads only four of it — `hide_icon`, `hide_cd_swipe`, `hide_cd_text`, `reverse_swipe`. The builder now takes a local `spellsFrame` and marks the rest `hidden`; `createDefaultBuffsSettings` no longer seeds `hide_active_swipe` / `hide_gcd_swipe` / `gcd_edge_charges`. Existing frames keep those keys in their saved settings, which is harmless — every reader of them is `spells`-only, and the `_swipeWatcher` predicate that also names them treats absent and `false` alike. Those setters raise `private.fontsDirty` around the refresh; they no longer have to — the aura trackers' `RESTYLE_KEYS` diff catches a move on its own (see `Components/BuffTracker.md`, which also audits what the pre-migration renderer genuinely lost here).

**The pandemic-glow group is the same panel, one release later.** It carried a second set of
widgets for a `DurationObject`-curve renderer that only CDM-routed frames ever used: the
animated `pandemic_glow_style` values, the Approaching/Urgent colours, both threshold sliders
and the LibCustomGlow opacity. Every frame type now draws its cue on Blizzard's native region
(`IconTracker` and both aura trackers all call `AuraContainer.SyncPandemic`), so those seven
widgets were removed and the panel matches the built-in trackers: toggle, the two border
variants, colour, thickness. The gate that split the two — `auraAf`, true only when the
component exposes `IsUsingSlots` — is gone with them, and with it the **greyed-out pandemic
toggle on `spells` frames**: `auraAf` was false there, so the toggle fell through to
`private.PANDEMIC_CURVE_DISABLED` and disabled a feature the renderer had supported since the
`spells` type moved onto the factory. That kill switch had no other reader and is deleted.
Style, colour and thickness now call `refreshSelectedFrame()` from their setters, matching the
tracker panel; without it they reached the profile and waited for an unrelated refresh.

Custom spells on an aura frame are consumed as a **map only** — `CustomSpells.rebuildComponent` returns before building a pool for any component whose `getComponentMode` is `"aura"`. A pool there would go unpositioned *and* draw every custom spell twice, once pooled and once through the container.

## Spells frames

`getIconTracker` builds the tracker lazily on first layout and caches it on `instance.iconTracker`; `applyFilteredLayout` dispatches to `applySpellsLayout` (tracker `Refresh`). `GetComponentSize` / `GetWantsContentWidth` delegate to it, exactly as the aura path does — the factory sizes its own wrapper, not `instance.container`, so reading the container rect would report the anchor system's last answer rather than the content box.

**One AF-side override on top of that delegation.** When `icon_visibility_mode` 2/4 hides *every* icon, the factory reports its `1x1` collapse sentinel — correct for the primary trackers, wrong here: `applyIconLayout`'s empty branch held an AF at its configured `width`/`height` precisely so anchored children keep their slot and the frame stays grabbable. `comp.GetComponentSize` restores that, returning `math.max(width or icon_size, 1)` × `math.max(height or icon_height or icon_size, 1)` when the frame is enabled, in mode 2 or 4, outside EditMode, **and** the tracker answered either `1x1` *or* `0x0`.

`0x0` is in that set because the factory short-circuits on `spellCount == 0` (`lastSpellCount + lastAppendCount`) *before* it reaches the hide-mode branch. An all-foreign frame — every `assigned_spells` entry a Trinket/Consumable/Racial — contributes no spell-map keys at all, so once the hide filter empties its append list both counts are zero and the answer is `0x0`, not the sentinel. Same collapse, same repair. With no hide mode configured `0x0` still passes through untouched: that is the genuinely-empty frame. EditMode is excluded too — the factory never collapses there (both early returns are `not private.isEditMode`-gated) and `comp.Refresh`'s min-size branch floors the container on top. The factory itself is untouched, so `CooldownTracker` / `UtilitiesTracker` still collapse to `1x1`.

> **The guard is deliberately NARROWER than the branch it restores, and is not "the same condition the old path used".** `applyIconLayout`'s empty branch keyed on `visibilityHidAll = visibilityActive`, i.e. `icon_visibility_mode > 1 and not isEditMode` — which **includes** the fade modes 3 and 5. This one fires on modes 2 and 4 only. That is correct rather than a gap, because a fade mode does not remove anything from the visible set: `Util.MakeIconVisibilityFilter`'s fade branch always `return false` (the icon stays in the append list), and the factory's pooled buttons get `cue_visAlpha = fadedAlpha`, which `layoutButtons` counts as visible. So a mode-3/5 frame can only read empty when it has nothing to draw at all — exactly the case that should fall through to `0x0`. The one seam: `icon_visibility_faded_alpha` has `min = 0` in the Options slider, so a user who sets it to `0` turns mode 3/5 into mode 2/4 for counting purposes and that frame *does* collapse where the old path held it. Known and unrepaired; the fix, if it is ever wanted, is to widen the guard to `mode > 1`, not to touch the counting.

**Background suppression.** `applySpellsLayout` calls `Util.SetComponentEmpty(instance.container, not visibilityActive and iconTracker.IsCollapsed())` after the refresh — the replacement for `applyIconLayout`'s `SetComponentEmpty` calls, which no longer run for any frame type. A frame that draws nothing hides its configured background; a frame emptied by a hide/fade mode does **not** (it is live, just momentarily empty — the old path passed `false` in that branch for the same reason). `comp.Refresh` re-applies `ApplyComponentBackground` immediately after the dispatch, so the flag takes effect in the same pass.

`hide_active_swipe` is seeded **off** in `createDefaultSpellsSettings`, as in 2.13.4 and as the
two primary trackers default: an active buff takes the icon over. `force_desaturation` is seeded
**off** again; frames created in 3.0 lack the key, which reads as off. 3.0's
`show_active_duration` is no longer seeded, backfilled, offered or read for a `spells` frame —
a key a 3.0 frame saved is inert. Frames created in 3.0 keep the `hide_active_swipe = true` they
saved (the user's call, 2026-09-28). See `Core/IconTracker.md`, "Aura takeover".

There is deliberately **no `AURA_TRACKER_BY_TYPE` entry for `"spells"`**: that table also carries a `viewerKey`, which a migrated spells frame has no use for, so `private.IconTracker.CreateTracker` is called directly. `CreateTracker` returns `(component, ctx)`; only the component is captured.

Hosting is identical to the aura path: the factory creates its own wrapper inside `instance.container` and `SetAllPoints` it, never repositioning the outer frame, and the tracker shares the AF's component name (`AdditionalFrame_<id>`) so its Anchor visibility/alpha/strata queries resolve to this frame's own settings.

**Container Show/Hide is content-only.** The factory's `container` local is the wrapper, a different frame object from `instance.container`; outer visibility stays Anchor-owned, and `applyFilteredLayout` returns before any layout call when `Anchor.IsVisibleForComponent` is false. If a migrated frame ever fails to hide, check *which* frame got hidden before anything else.

**A font edit made while hidden is owed, not lost.** Both hidden returns — `comp.Refresh`'s and `applyFilteredLayout`'s — set `instance.fontsOwed` when `private.fontsDirty` is up, and the next shown `applyFilteredLayout` raises the flag around its one dispatch to the hosted tracker (only if the caller had not). The pass that reveals the frame (a target gained, a dismount, the hide-rule pull) carries no font pass: under a `no_target` hide rule one ran on every target gained or lost and restyled every aura button of every tracker (`Core/Anchoring.md`).

Five config fields carry the AF's semantics into the shared factory:

| Config field | Purpose |
|---|---|
| `parent` | `instance.container`. This is what makes the tracker *hosted*: the factory parents its wrapper here and `SetAllPoints` it instead of creating a top-level frame on `UIParent`. |
| `getSettings` | `private.profile.additional_frames[id]`. Without it the factory reads `private.profile.components[name]`, which is nil for an AF. |
| `buildSpellMap` | `buildAFIconSpellMap` — this frame's `assigned_spells` minus every `ADDON_ICON_SOURCES` entry **and minus every CDM entry the character does not have** (see below), plus `CustomSpells.GetSpellMapFor`. No aura identity-set widening: these are cooldowns, keyed by the base spellID the CDM and the pickers use. Custom spells go through the API, never a raw `settings.custom_spells` walk, because the API applies `shouldFilterEntry` (drops spells the player's talents have replaced). |
| `getOrderRank` | `buildAFOrderRank` — a flattened port of the old `spellOrderByViewer` (one map, no viewer dimension). Rank = `assigned_spells` index; a spec override is registered at its base entry's index so either id lands in the same slot; custom spells take `#assigned_spells + i`, and a spell that is both assigned and custom keeps its assigned position. Returns a **reused module table** (`afRankScratch`), wiped per call — the factory copies it before adding synthetic keys and never holds it. Without this hook the factory falls back to `Util.BuildSpellOrderRank`, which returns nil for any non-CDM component, so an AF would sort by ascending spellID. |
| `getAppendRank` + `hooks.getAppendFrames` | Foreign icons (see below) ride the same grid and are ranked in the same index space instead of always landing last. |

## Addon icon sources

"spells"-type frames can also source icons from other addon components:

- TrinketTracker (source `"Trinket"`, id = slot 13/14)
- ConsumableTracker (source `"Consumable"`, id = category ID: 1=combat, 2=health, 3=mana, 4=healthstone, 5=utility)
- RacialTracker (source `"Racial"`)

`collectAFAppendIcons` is the factory's `hooks.getAppendFrames`. It **releases everything it holds and re-adopts** on every pass, like CooldownTracker's collector: with a handful of icons that is cheaper than diffing, and it is what returns a de-routed icon to its source component (which only lays out icons `IsSpellRouted` no longer claims). Release restores `SetIgnoreParentAlpha(false)` **and the parent's strata** — source components never set strata explicitly, so without the restore a de-routed icon stays stuck at this frame's strata. Adoption sets `SetIgnoreParentAlpha(true)`, this frame's effective strata, and this frame's fonts (`applyAFAppendIconProperties`, the AF twin of CooldownTracker's `applyAddonIconProperties`) — the icon belongs to another component, which would otherwise style it from *its* settings.

Ranks are recorded alongside the frames in `instance.afAppendRanks`; `getAppendRank(frame, index)` is a plain array read. A rank is the entry's `assigned_spells` index plus a fractional sub-order (`i + (k-1) * 0.001`) when one entry yields several icons — a single consumable category can. Equal ranks would fall through to the factory comparator's id tie-break, and the factory keys foreign frames by *negative* synthetic ids, so a tie there reverses append order.

**Why the two collectors cannot double-draw:** every `assigned_spells` entry is dispatched by `ADDON_ICON_SOURCES[source]` to exactly one of them. `buildAFIconSpellMap` skips addon-source entries, `collectAFAppendIcons` handles only addon-source entries, and neither reads the other's half.

**`assigned_spells` is intersected with the character's own CDM entries.** It is *profile* data, so it outlives a character and a spec change and accumulates entries for classes and specs the player is not on. The pre-migration renderer collected live viewer children, and Blizzard only creates a child for an entry that passes its own display gate (category + `isKnown` + not `isInvisible`), so the filter came for free; the migration replaced collection-from-children with build-from-profile and lost it, and a spells AF began drawing other classes' spells. `CDMDataSource.IsCooldownSpellTracked` restores it — `CooldownEssential` + `CooldownUtility` only, which is exactly a spells frame's source set (`SPELLS_VIEWER_KEYS`) and is consistent with `migrateAdditionalFrames` treating buff-source spells here as *orphaned*.

Two properties matter:

- **It fails OPEN.** The accessor returns `nil` while the resolved model does not exist yet — components enable on `PLAYER_LOGIN` while `CDMDataSource.Initialize()` waits for `LOADING_SCREEN_DISABLED` — and `nil` means *draw it*. Intersecting against an unbuilt model would empty the frame instead. It self-corrects: this map is rebuilt on every tracker `Refresh` (never cached), and the factory's `OnCDMSpellsChanged` registration fires after every invalidation. The nil test is written as an explicit `tracked == nil or tracked == true`, **not** the `and`/`or` ternary, which collapses on a falsy middle operand and would silently re-admit every untracked spell.
- **Custom spells bypass it.** They are explicit user entries, not CDM data, and `CDMDataSource.BuildComponentSpellMaps` merges its `customMap` with no `isKnown` test either — filtering them here would diverge from the primary trackers.

Covered by `.superpowers/sdd/checks/afroute_check.lua`, which drives the real extracted source of both halves.

**Borrowed-icon state has an owner, and it is us.** Whoever sets an alpha override, starts a fade, or zeroes the inner textures of a frame it does not own must clear that state when the frame goes back — **including the frame's own alpha**. `Util.MakeIconVisibilityFilter` writes *two* things: the side-table override, and the frame itself (`child:SetAlpha(0)` in the hide branch, `StartIconFade` to `icon_visibility_faded_alpha` in the fade branch). Neither is repaired for us. The source component's flat `SetAlpha(1)` does not survive, because *every* writer of a routed icon's alpha multiplies `Util.GetIconAlphaOverride` back in (`patterns.md`), so a leftover override outlives the repair; and only a **trinket or a combat potion** is re-alphaed by a new owner at all — `CooldownTracker.collectRoutedAddonIcons` reclaims equip slots 13/14 and consumable category 1 and nothing else, so `RacialTracker`, `TrinketTracker` with `route_trinkets` off and `ConsumableTracker` categories 2–5 never touch a per-icon alpha (all four components only ever `SetAlpha` their *container*). Miss either half and a de-routed racial comes back permanently dim under fade modes 3/5, and **invisible until `/reload`** under hide modes 2/4.

`clearAFForeignIconState(icon)` is the undo (`CancelIconFade` + `icon:SetAlpha(1)` + `SetIconAlphaOverride(nil)` + `RestoreInnerTextures` — the `SetAlpha(1)` in the same shape `CooldownTracker.clearRoutedAddonIcons` uses, and after the cancel because `CancelIconFade` only stops the animation and writes no alpha), and `releaseAFForeignIconState(instance, keepToken)` decides who gets it. It cannot key off `addonIcons`: a hide-mode icon is filtered *out* of the append list and never enters that table, yet it is exactly the icon carrying an override of `0`. Instead `collectAFAppendIcons` stamps every candidate it **evaluates** into `instance.afForeignSeen` with a monotonic pass token (`instance.afForeignPass`), before the filter runs, and sweeps anything still carrying an older token at the end of the pass. The token is what makes release-then-re-adopt survivable — a flat per-pass clear would cancel an in-flight fade on every layout pass and restart the animation from wherever it had reached. Full-release call sites (`getAppendFrames(false)`, `comp.OnDisable`, `deactivateFrame`) pass `nil` and clear everything.

The original components continue managing data/cooldown/glow updates; the AF only handles rect, alpha, strata and fonts. The AF component's `SyncAlpha` forwards to its spells or aura tracker, so Anchoring's visibility-only pass (target changes, a fade-only pull) re-alphas the frame's icons too — they ignore container alpha (spells) or sit in a container frozen in combat (aura types). `OnAddonIconRefresh()` is called by components after their refresh cycle to trigger re-layout of affected additional frames. Instance field `addonIcons` still tracks adopted icons — `applyFilteredLayout`'s invisible branch and `comp.OnDisable` both walk it.

## Cursor following

Setting `anchor_parent = "cursor"` makes the frame track the mouse pointer in real-time via an OnUpdate handler using `GetCursorPosition()` scaled by `UIParent:GetEffectiveScale()`. Reuses existing `anchor_profile` fields: `anchor_side` determines which edge of the frame aligns to the cursor (mapped via `CURSOR_SIDE_TO_POINT`), `anchor_offset_x/y` offset from the cursor. Suspended during EditMode. Both settings panels treat a cursor-following frame as anchored, like any component with an anchor parent: Anchor Side and the anchor offsets are live, while Anchor Point, Frame Point, the free-move offsets and the width mode/percent controls are disabled (Options) or hidden (Edit Mode), since none of them is read in this mode. Cursor-following frames are excluded from the anchor_parent dropdown to prevent other components from anchoring to a moving frame.

## Proc glow hooks

Every frame type gets `proc_glow_*`, `active_glow`, `pandemic_glow`, and the ready flash from its own factory tracker's engine — there is no AFM-level hook installation any more. The `hooksecurefunc`-based hooks that used to watch matched CDM viewer children directly (`installProcGlowHooks` / `installPandemicHooks`, and the per-child overlay bookkeeping they owned) were part of the pre-migration cross-parenting renderer and were deleted with it.

A spells frame's pooled buttons get proc glow from the `IconTracker` factory (`applyProcGlow`) and pandemic/active glow from `AuraContainer.SyncPandemic` / `AuraContainer.AttachPandemic` — Blizzard's native, engine-driven `AddPandemicRegion` mechanism, the same one the two primary icon trackers use and the same one aura-type (`buffs`/`bar`) frames always used. Because that mechanism hands Blizzard an addon-owned region and lets the engine `SetShown` it, the pre-12.1 gap where the pandemic overlay went dark while auras were secret (a `DurationObject`-driven alpha curve that Lua-errors on a secret `auraInstanceID`) no longer applies to any Additional Frame type — that gap was specific to the old CDM-cross-parenting path.

`createDefaultSpellsSettings` carries `cdm_glow_color` (same `{1, 0.843, 0, 1}` default as the two primary trackers) for the ready flash, which `GlowEffect.PlayReadyFlash` leaves untinted when the key is nil. The Options colour picker for it is gated on the key in both builders: `buildComponentSpecificWidgets` for the two trackers, and the AF panel's `addGlowSuite` for spells frames (added 2026-09-30, #5; until then a spells frame's flash was stuck on the default gold). Edit Mode has no picker for it on either. The setter pushes nothing: `PlayReadyFlash` reads the live setting on every flash.

## Tracker teardown

`deactivateFrame` calls `OnDisable()` on whichever tracker the instance owns (`auraTracker` / `iconTracker`) before unregistering the component. This is not optional bookkeeping: `manager.OnProfileChanged` deactivates **and reactivates every additional frame on every profile switch**, and `activateFrame` builds a fresh `instance` table, so without the call the old tracker's container, pooled buttons, aura slots and `SPELL_UPDATE_COOLDOWN` / `UPDATE_BINDINGS` registrations are abandoned while still live. `OnDisable` self-guards its Show/Hide half on `InCombatLockdown()`, so an in-combat profile switch degrades the same way the rest of that path already does. Frames are never garbage collected in WoW, so the orphaned container itself lingers as a hidden ghost until `/reload` — what the call reclaims is the event traffic and the per-frame watcher work.

## Profile migration

On load, `migrateAdditionalFrames()` first gives any frame without `assigned_spells` an empty list — every frame this addon creates has one, but an imported frame need not, and the migration itself, `rebuildSpellRouting` and `OnAddonIconRefresh` iterate it unguarded (`isSpellRoutedToBarProfile`, which can run before the migration, guards its own read). It then converts legacy `frame_type = "icon"` profiles to `"spells"`, normalizes `assigned_spells` entries (strips source for CDM spells, keeps `{id, source}` for addon sources), and notifies the user about orphaned buff-source spells that need reassigning to a buffs frame. A trailing backfill pass adds default keys introduced after a frame was created — including `always_show_tracked` on the two aura types, which otherwise reads as `nil` and leaves the Options toggle with nothing to bind to.

## Fonts

On a **spells** frame the fonts belong to the `IconTracker` factory, which owns the pooled buttons, their countdown Font object and their keybind FontStrings; the AF's only font duty is `applyAFAppendIconProperties`, which restyles adopted foreign icons (timer / keybind / stacks) from this frame's settings on every collect pass. The pre-migration viewer-child renderer's own keybind overlay (`applyKeybindTextForAdditionalFrame` and its `keybindFontStrings` pool) has been deleted along with it — it had no live caller.

## Icon visibility mode (spells-type frames)

`settings.icon_visibility_mode` (1–5) removes icons from a spells-type frame's layout based on their current state; the container resizes to match. Values mirror CooldownTracker/UtilitiesTracker: 1=Disabled, 2=Hide When Ready, 3=Fade When Ready, 4=Hide When On Cooldown, 5=Fade When On Cooldown.

Post-migration the mode is evaluated in **two places**, because the grid holds two kinds of frame:

- **Pooled buttons** — the `IconTracker` factory's own `cue_visAlpha` machinery, driven by its `SPELL_UPDATE_COOLDOWN` watcher with a membership-gated `Refresh` (identical to the primary trackers).
- **Foreign icons** — `collectAFAppendIcons` runs `ensureExcludeFilter(instance)` per icon, the same `Util.MakeIconVisibilityFilter` closure the old path used, with `isReadyAddonFn = isAddonIconReady` (reads `icon.wasOnCooldown`, plus `C_Spell.GetSpellCharges` for charge spells). Hide modes drop the icon from the collected list; fade modes keep it and park it on an alpha override. `IconTracker.placeIconButton`'s foreign-icon branch and `SyncAlpha` both multiply `Util.GetIconAlphaOverride` in and skip an in-flight fade, so the factory cannot flat-write over a fade the filter started.

`ensureExcludeFilter` is the single construction site for that closure; the filter is cached on `instance._excludeFilter` because its per-child debug throttle has to survive across passes.

Re-evaluation of the *foreign* half rides `manager._swipeWatcher`, which already re-runs `applyFilteredLayout` on `SPELL_UPDATE_COOLDOWN` (coalesced to one pass per rendered frame) for any frame with `icon_visibility_mode > 1` or a swipe setting. `applySpellsLayout` additionally calls `updateIvmWatcherEvents(instance, active)` to keep `SPELL_UPDATE_USABLE` / `ACTIONBAR_UPDATE_COOLDOWN` registered on that watcher while a hide/fade mode is active, via the refcount `instance._cueIvmActive` / `manager._cueIvmCount`. `SPELL_UPDATE_COOLDOWN` alone covers spell cooldowns; trinkets, consumables and racials are item/action cooldowns whose readiness can transition without one, and a usability-only transition fires neither.

> There is deliberately no 0.5 s polling ticker — the two events above cover what one would poll for, and `performance.md` documents repeated regressions from timer/per-frame work in these paths.
>
> **Why not `icontracker_config.extraWatcherEvents`?** The factory's per-event pass (`onSwipeUpdate`) walks only its own pooled `activeButtons` and escalates to a full `Refresh` solely on a *pooled* membership change. Foreign icons are re-collected and re-filtered by `hooks.getAppendFrames`, which runs only inside `layoutButtons`, i.e. only inside a full `tracker.Refresh()`. The AFM watcher's handler calls `applyFilteredLayout`, which *is* that full path, so the registration belongs there.
>
> **Pre-existing:** `deactivateFrame` does not decrement `_cueIvmCount` (only `comp.OnDisable` does), so a profile switch leaves the count incremented and the two events registered until reload. The handler early-outs per instance, so the cost is one extra settings check per event.

`settings.icon_visibility_treat_charging_as_on_cd` (default `true`) controls charge-spell semantics symmetrically across CDM and addon-owned icons. With the toggle on (default), `isAddonIconReady` also folds `chargeInfo.isActive` into the ready check so a 1/2 spell mid-recharge counts as on cooldown — matching the CDM-child path. With it off, only the zero-charge state counts as on cooldown (a 1/2 spell stays "ready"). This is a behavior change on upgrade: existing AF profiles default to `true` and will start hiding/fading charge spells at 1/2 instead of 0/2, unifying with the CDM-side semantics. Flip the toggle off per AF instance to restore the historical "1/2 = ready" behavior.

`settings.hide_ready_blink` (default `false`, spells-type only) suppresses the ready flash independent of `icon_visibility_mode`. **What it gates changed with the migration.** The old renderer's `hide_ready_blink` suppressed Blizzard's own cooldown-overlay **bling** (the gold swipe-completion sparkle) on borrowed CDM viewer children, via a shared-viewer consumer registration (`private.Util.SetFlashSuppress` / `IsFlashSuppressed`, read by `ApplySwipeToChild`) that was **orphaned** by the renderer's removal — the only callers this repo ever had were `applyIconLayout`'s four `ApplySwipeToChild` sites. All three were deleted in a follow-up increment, together with `ApplySwipeToChild` itself, its three `GetOrCreate*` overlay factories, and the six per-child state tables behind them (`desatOverlays`, `addonCooldowns`, `gcdCooldowns`, `swipeSuppressedActive`, `swipeSuppressedGCD`, `auraColorApplied`) including their `private.Util` exports. Nothing in the addon renders a CDM viewer child any more, so that whole path went with the renderer. The `IconTracker` factory's pooled buttons never draw that bling at all — `button.cue_Cooldown:SetDrawBling(false)` is unconditional, because a CDM icon never had one (`CooldownViewer.xml` declares no `BlingTexture`) while `CooldownFrameTemplate` does, and it is suppressed to avoid a swipe-completion sparkle the pre-12.0 CDM never showed. So on a migrated frame `hide_ready_blink` instead gates the addon's own ready-flash glow (`GlowEffect.PlayReadyFlash`, read directly off `settings.hide_ready_blink` in `IconTracker.lua`) — visually similar (a flash on the ready edge), but a different effect than the one the setting originally named.
