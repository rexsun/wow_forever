# BuffTrackerBars

Renders buff/proc aura **progress bars** via Blizzard's 12.1 AuraContainer (`CustomAuraContainerTemplate`) through the `Core/AuraContainer.lua` facade. CDM category `BuffBar` is a **data source only** (`Core/CDMDataSource.lua` `BuildComponentSpellMaps`, "BuffBar" domain — CDM spells minus Additional-Frame-routed ones, plus custom spells); the Blizzard `BuffBarCooldownViewer` frame is alpha-suppressed and never rendered. Left of CooldownTracker by default.

Defaults: bar_width 220, icon_size 30, bar_height 30.

**Containers:** three, since a container has exactly ONE unit and per-group `SetUnit` is deferred to 12.1.5 — the architecture for the whole 12.1 cycle, same shape as BuffTracker. Frame names take the instance `prefix` (`CUE_BTB` for the primary, `CUE_AF_<id>` for an Additional Frame). One aura group each:

| group | container | filter | carries |
|---|---|---|---|
| `<name>_main` | `<prefix>_Container_Aura` (player) | `HELPFUL\|PLAYER\|INCLUDE_NAME_PLATE_ONLY` | self buffs / procs |
| `<name>_target_harmful` | `<prefix>_TargetContainer_Aura` (target) | `HARMFUL\|PLAYER` | own DoTs / debuffs |
| `<name>_target_helpful` | `<prefix>_TargetHelpfulContainer_Aura` (target) | `HELPFUL\|PLAYER\|INCLUDE_NAME_PLATE_ONLY` | own buffs on an ally target |

`buildSpellMap` **merges** `BuildComponentSpellMaps`' two return maps into one and feeds it to all three — the filter strings decide where each aura can actually match. There is no self/target split: Blizzard's own CDM watches every tracked spell on both units (`scanUnits = { "player", "target" }`, `CooldownViewerItemData.lua:1`) and never reads the `selfAura` DB2 flag. Filters mirror Blizzard's `GetTargetAurasFilterString` (`:661`). A `PLAYER_TARGET_CHANGED` handler calls `UpdateAllAuras()` on both target containers — `SetUnit` early-outs on an unchanged token, so a target *swap* fires no container-side refresh on its own.

**The target-HELPFUL group has a container to itself** so it can be hidden while the player targets themself, which is otherwise a duplicate of the player-HELPFUL group. `syncSelfTargetSuppression()` toggles it with `SetShown` (unrestricted, unlike every container API call) from the target-change handler and from the end of `Refresh`. It is chained LAST in the layout, so hiding it leaves no gap. Per-spell `aura_unit` (`"player"` / `"target"` / default `"both"`) restricts which of the three a spell may appear in. Both are covered in full in `Components/BuffTracker.md` and `.context/patterns-auracontainer.md`.

Each pooled AuraButton renders as `[icon | status-bar fill + name text | timer]`, built once per button by the local `makeBarInit`: `cue_Icon`, `cue_Count` stack text on the icon, `cue_Bar` (plain StatusBar bound with `SetDurationBar`, `RemainingTime` direction so it drains — Blizzard drives the fill level), `cue_Name` (bound with `SetSpellName`), and `cue_Timer` (plain FontString bound with `SetDurationText`). All regions are children of the forbidden-object button, `cue_`-prefixed (see `.context/patterns-auracontainer.md`). Geometry is *not* set at creation — `applyBarGeometry` owns it, so `makeBarInit` and the restyle path can never disagree.

**Layout — 1:1 with the old `Util.LayoutViewerBars`:**

| Old engine | Here |
|---|---|
| `bar_width` = FULL item width (icon sits *inside* it) | `itemDims` — **not** `icon + spacing + bar` |
| percent-mode anchor width replaces `bar_width` | `Anchor.GetInheritedWidth` (already percent-gated) |
| `bar_content == "IconOnly"` **and `collapse`** → width = `icon_size` | same, and it wins over inherited width. The shrink is opt-in: with `collapse = false` an IconOnly row renders at the configured `bar_width` / inherited width. `GetWantsContentWidth` reports true for the collapsed case so the box hugs the icon width (slots only — §D4 keeps a fixed estimate under groups). |
| item height = `ComputeBarItemHeight` (`max(bar_height, icon_size)`, or `bar_height` when the icon is hidden) | shared helper, same call |
| `layout_direction` | `SetFlowLayoutAxis` |
| `layout_alignment` left/right (h) or top/bottom (v); **"center" falls back to `growth_direction`** | same fallback, verbatim |
| `growth_direction` | flow growth direction + the anchored edge |
| bars never wrap | `SetFlowLayoutMaximumLineSize(nil)` → `math.huge` |
| `bar_spacing` between items | `elementSpacing` / `lineSpacing` |
| square icon at BOTTOMLEFT + `icon_offset_x/y`, overhanging above the bar when `icon_size > bar_height` | `applyBarGeometry` |
| bar occupies the bottom `bar_height` strip, left-offset by `icon_size + icon_offset` (0 when the icon is hidden) | `applyBarGeometry` |
| `bar_content` icon/name visibility, `show_timer` | `applyBarGeometry` |

Each container is pinned to its own wrapper at the **same** point as the flow anchor — its rect is engine-owned and secret, so only that point sits at a known wrapper position. The direction contract is derived once in `barFlow` and shared by both engines, so the groups flow and the slots stack can never disagree. Under groups the target wrapper continues the run after the player section, offset by a `sectionSize` estimate built from the **mapped** count — the real section extent is secret, so the estimate over-reserves whenever part of the player set is inactive (the same tradeoff BuffTracker makes). `SyncGroup` runs on every Refresh with the per-group sync-signature skip (unchanged spell set + layout = no engine calls). AuraContainer layout calls are combat-restricted, so `Refresh` bails under lockdown; the combat-exit layout pass (`Core/Anchoring.lua`'s `OnLeaveCombat`, which runs `ContentLayout` = `Refresh`) catches up.

**Restyle path:** `restyleBarButton` runs `AuraContainer.ApplyTooltip`, re-runs `applyBarGeometry`, applies the global `bar_fill_color` fill (the per-spell `spell_colors` override is layered on top afterwards in slots mode — see above), and routes `name_font` / `duration_font` / `stacks_font` through the shared `Util.ApplyFontProfile` — which carries the profile's `anchor_point` / `offset_x` / `offset_y` positioning and justification, matching the old `Util.ApplyViewerBarFonts` (name and duration parented to `cue_Bar`, stacks to `cue_Icon`, or to the button itself on a slot button, where the icon is chrome on the cell; name width-capped to 80% of the inner bar with word wrap off). Every guard in it is nil-safe, so the one function serves both group buttons (full widget) and slot buttons (adornments only). Wired through the facade's dirty-flag system: `RegisterTracker` before `makeBarInit`, acquire-time initial styling, `MarkDirty` on `OnProfileChanged`, `private.fontsDirty` bridged in `Refresh`, `RestyleIfDirty` walks tracked buttons. `Refresh` also diffs the file's `RESTYLE_KEYS` list against the values it last saw, so `bar_height` / `icon_offset_x` / `icon_offset_y` / `collapse` / `show_timer` / `bar_fill_color` apply live even from a setter that never raises the flag — add a new restyle-applied key there, not to the setter.

**Visibility:** same as BuffTracker — an unprotected wrapper, laid out, shown and hidden in combat like any other component, `Hide()`n rather than parked at alpha 0; `SyncAlpha` for the lightweight alpha-only sync. Collapse transitions notify `Anchor.OnComponentStateChange`.

**Two engines, one per display mode** — same contract as BuffTracker, selected from `always_show_tracked` (Blizzard's BuffBar "Hide when inactive" is copied in once by `pm.MigrateHideWhenInactive` and never read again). `AddAuraGroup` compacts the secret active set for hide-when-inactive; `AddAuraSlot` ×N holds a static stack for always-show. **Groups is the default** — `always_show_tracked` defaults to `false`, matching Blizzard's own shipped `HideWhenInactive = 1` for every CooldownViewer system (`EditModePresetLayouts.lua:672-741`), so the slots-only features here (`spell_colors`, `active_glow`, `icon_overrides`, auto-resize) are off out of the box. **The Options panel hides what the active engine cannot deliver** — `active_glow` + its color, the whole `proc_glow` suite, `spell_colors` and `overflow_icon_size` are absent (not greyed) while groups is in force, in the trackers tab and on every Additional Frame. The gate is `tracker.IsUsingSlots()`, the same single mode read the layout uses, so panel and layout cannot disagree; toggling "Always Show Tracked Auras" re-renders the panel so the widgets follow. `icon_overrides` is a global profile tab, not per-component, so it is never hidden. **`always_show_tracked`** (Options → "Always Show Tracked Auras", default `false` = groups) is the engine switch. Turning it on gives up compaction — only groups can compact. With it on, **`desaturate_inactive`** ("Desaturate Inactive Auras", default `false`) greys a row's icon while its aura is not up — see `Core/AuraTrackers.md` "Desaturated inactive icons". See `.context/migration-parity-gaps.md` "Groups — the degraded engine — is the DEFAULT". The idle engine takes `includeSpellIDs = {}` and holds zero frames, which is how the switch works without a removal API.

**Always-show (slots).** Bars are the best case for the role split — background-plus-fill is normal bar construction, so there is no compositing artifact even in principle. Our plain `cell` Frame owns the persistent chrome: `cue_Bg` (the bar-strip backdrop), `cue_Icon`, and `cue_Name` — the name is set straight from `C_Spell.GetSpellInfo` rather than bound with `SetSpellName`, because under slots we know the spell and a bound name would vanish with the button. The name alone sits on a raised child frame of the cell (`AuraContainer.CreateTextLayer`): the cell is held at the wrapper's frame level, so a plain cell region would draw under the slot button's fill. The slot button carries only `cue_Bar` (`SetDurationBar`), `cue_Timer` (`SetDurationText`), and `cue_Count` (`SetApplicationCount`), and is `SetAllPoints`'d to its cell inside `initializeFrame` (before the provider applies access restrictions), so only the cell is ever moved afterwards. `restyleBarCell` mirrors `applyBarGeometry`'s contract for the persistent half — square icon at BOTTOMLEFT + `icon_offset_x/y`, the strip occupying the bottom `bar_height` to its right, `bar_content` visibility, `name_font` through `Util.ApplyFontProfile`. Under **groups**, both containers live inside `CUE_BTB_Pair`, a bounds frame (`wrapper` → `pairFrame` → the two bare containers via `AuraContainer.CreateContainer`). The target block is chained directly onto the end of the player block — `targetContainer:SetPoint(anchorPt, container, trailingPt, ±spacing)` — so the two abut exactly and the seam tracks the live bar count; `barFlow`'s anchor points are cross-axis MID-edge points (`"TOP"`/`"BOTTOM"` for a column, `"LEFT"`/`"RIGHT"` for a row), so the chain keeps the blocks centred on one line as well as gapless. `pairFrame:ResizeToBoundsRect()` (preceded by `SetSize(0.001, 0.001)`, or the frame could only grow) then sizes the bounds to both blocks engine-side, and a single `SetPoint(anchorPt, wrapper, anchorPt)` places the **pair** as a unit. Driven from an `OnUpdate`, since compaction changes the extents whenever an aura comes or goes and `Refresh` bails in combat; slots mode clears it. All estimate-free — the earlier settings-derived offset reserved room for every tracked aura, and `sectionSize` existed only for that and is gone. See `.context/patterns-auracontainer.md` "`Frame:ResizeToBoundsRect()`".

**A summon's own CDM row never fills, in either engine — known and unfixable.** A CDM tracked-buff entry for a summon — Demonology's Dreadstalkers, Demonic Tyrant, Charhound — applies **no player aura**, so no candidate filter can ever match it. Blizzard's own buff item reads `GetTotemData()` *before* the aura (`CooldownViewer.lua:1352`); addon code cannot follow: `C_Secrets.ShouldTotemSlotBeSecret` answers `true` for every *occupied* slot, so the data is secret in exactly the case that matters, and nothing anywhere says which slot holds which spell. Under always-show the row draws its chrome and never moves; under groups it does not appear at all. A guarded totem fill on the chrome cell was built and reverted the same day — read `.context/patterns-cooldownviewer.md` "A tracked buff has TWO duration sources" before touching this, including the rejected `UNIT_SPELLCAST_SUCCEEDED` → `PLAYER_TOTEM_UPDATE` correlation.

**`show_totems` (Features → *Track Totems*, default off) is the display that does reach them**, and it is a different thing from that row: one bar per totem **slot**, never asking which spell is in which slot. The rows **trail the run**, after the aura bars. Each sits in a slot frame inside the bounds frame, sized to the row plus one `bar_spacing` and created with `DisableUntrustedLayoutScriptsTemplate`, and the slot frames chain with no offset, each collapsing while hidden, so an empty slot takes its spacing with it. Under groups the chain starts on the target-helpful container's trailing edge, which the engine resolves without Lua reading it. Under slots it starts on the last spell cell. Inside the bounds frame the rows move with it, so the groups stack follows BuffTracker with totem rows on as well. One row is placed per slot whether occupied or not, driven by a 0.25 s poll. The poll `Hide()`s a slot whose `GetTotemDuration` is `nil` (empty — the sink rejects nil), so the chain closes the gap. It pipes every other slot blind, `haveTotem` included, without ever testing a totem value. Each row's countdown is a `C_DurationUtil` text binding, which needs the default aura formatter: `SetToDefaults` clears it, and without one no timer is drawn. `C_Secrets.ShouldTotemSlotBeSecret` is not consulted: it has answered `false` for a slot whose reads came back secret. Full contract and the three consequences that constrain any change to it: `Core/AuraTrackers.md` "Summons: the CDM row never fills, and a slot row is what replaces it".

Under **slots**, all three slots of a spell (player-HELPFUL, target-HARMFUL, target-HELPFUL) share ONE cell, so a spell occupies a single row regardless of which unit its aura lands on; placement is a single run down (or across) the wrapper over that one cell array, using the same `barFlow` derivation the groups path hands the flow layout. Bars never wrap in either engine.

**Bar order is slots-only.** `priority_order` (Options → Icon Order, see `Components/README.md`) orders that shared cell array through `fillSortedList`, so under slots the arrangement IS the stack. Under **groups** Blizzard flows the container with `AuraContainerSortMethod.Default` and there is no addon-side lever; unlike BuffTracker there is no per-spell-groups engine here, so slots is the only ordered engine.

Each container gets **its own cell array** (`selfCells` / `targetCells`), switched via the `cellPool` upvalue around each `SyncSlots` call: the two slot index spaces are independent, and a shared array would re-key the target cells whenever the player count changed, leaving already-created buttons anchored to the wrong cell. A **target** cell holds two slot buttons (harmful + helpful) since only one filter can match at a time, so `cell.cue_buttons` is a list rather than a single reference.

**Per-spell `spell_colors` (§D5) works under slots.** `applyBarFill` reads `settings.spell_colors[spellID]`, falling back to the global `bar_fill_color`, and is applied to every button on the cell. This is exactly what groups cannot do — there the container assigns auras to pooled buttons and that binding is secret, so there is no spellID to key the override by. `layoutBarCells` runs **after** `RestyleIfDirty` in `Refresh`, deliberately: `restyleBarButton` resets every bar to the global color, and the layout pass is what re-applies the per-spell override on top.

**Sizing is engine-gated.** Under **slots** it is the real stack extent — `itemDims` per bar × the live count (both sections summed) plus `bar_spacing` gaps, i.e. exactly what `layoutBarCells` placed — and `GetWantsContentWidth` is true only for a HORIZONTAL run, since a vertical stack's width is still the configured (or inherited) bar width. Under **groups** it stays FIXED (decision 2026-07-26): the configured `height` with a width following the anchor-inherited size when there is one, exactly as `itemDims` does for the bars themselves, so the box can never be narrower than its bars. It previously derived the along-axis extent from `lastSpellCount`, the *mapped* count, which over-reserves permanently while looking dynamic to the anchor system. Empty and out of Edit Mode reports 0×0 in either engine so the anchor gap closes; in Edit Mode the configured box keeps the frame grabbable when empty. See `.context/migration-parity-gaps.md` "Groups — the degraded engine — is the DEFAULT".

**Sitting on BuffTracker, the bars follow its visible buffs, not its box.** BuffTracker's groups box is fixed too, so bars anchored to its top used to float a whole box-height above the cooldowns with no buff up — 2.13.4 read the viewer's shown children and collapsed, 12.1 made that secret. Under **groups**, when `anchor_parent` is BuffTracker and the column grows away from it (side Top + growth up, Bottom + down), `syncContainerLayout` pins `CUE_BTB_Pair` to BuffTracker's bounds frame (`tracker.GetBoundsFrame()`, `CUE_BT_Pair`) at the facing edge plus the anchor offsets, instead of to the wrapper. The engine sizes that frame to the buffs actually showing, so the bars sit on the buff row and drop onto whatever is below BuffTracker when it empties. `followTarget` decides it: any other side/growth pair, a collapsed or disabled BuffTracker, and the slots engine keep the wrapper pin. Legal only because our bounds frame already carries the forbidden aspect (`.context/patterns-auracontainer.md` "`Frame:ResizeToBoundsRect()`"). The wrapper — Edit Mode box and anything anchored to this tracker — stays where the anchor system puts it. Re-evaluated on every out-of-combat `Refresh`; a BuffTracker collapse or enable change triggers one through `Anchor.OnComponentStateChange`. BuffTracker's bounds frame stops resizing while its wrapper is hidden, so bars that stay shown then follow its last extent. Pinned by `tests/barfollow_check.lua`.

**Custom spells:** merged into the same aura groups via `CustomSpells.GetSpellMapFor` (scoped by the entry's `specs`, not `restrict_to_player` — `Core/README.md` "Custom spells"); no separate custom-bar frames. They carry no self/target knowledge, so each lands in both maps and the filter strings decide where it can match — an entry whose `unit` is `focus` matches nowhere, since there is no focus container — the Options unit dropdown therefore offers only Player/Target on this component (see `.context/patterns-auracontainer.md` "Per-spell unit scope").

**Tooltips** are the aura button's own, not `Core/UI/Tooltip.lua` — the button already owns one and knows the secret aura behind it, which our tooltip cannot. `tooltip_mode` / `tooltip_anchor` are mapped onto `SetMouseMotionEnabled` / `SetHideTooltipInCombat` / `SetTooltipAnchorPoint` by `AuraContainer.ApplyTooltip`, so they work in **both** engines. `out_of_combat` needs no combat callbacks (Blizzard re-evaluates per show). See `.context/patterns-auracontainer.md`.

**`active_glow`** works under **both** engines and needs no aura read: the border is created on the aura button itself (`GlowEffect.CreateActiveBorder`, built lazily by `ApplyActiveGlow` so every init path gets one), so the engine's show/hide of that button is the glow, and `AuraContainer.ApplyActiveGlow` carries only the on/off and colour on the restyle path. Unlike `spell_colors` it therefore needs no per-spell key. It also stopped reading `CDMDataSource.GetAuraState`, which means it no longer goes dark with the CDM CVar off and a **custom** spell (no viewer child) now glows like any other.

**`proc_glow`** is **slots only**, same binding reason as `active_glow`, but needs no CDM bridge — `C_SpellActivationOverlay.IsSpellOverlayed` answers from the spell ID alone, and the ID queried is *ours* rather than the event payload's (which carries the *overlayed* ID and diverges under an override). It rides the chrome **cell** through the same `AuraContainer.SyncProcGlow` the icon trackers use, unchanged. Driver is a `SPELL_ACTIVATION_OVERLAY_GLOW_SHOW`/`_HIDE` pair that `Refresh` registers only while slots are live and the style is not `"none"`. Default style is **`"border"`** here, not the icon trackers' `"blizzard"`: the proc atlas is square art stretched to the host rect, which reads wrong across a wide bar. Every style stays selectable. Added 2026-08-18 — bars had no proc glow at all before then (it was never lost in the migration; the CDM wrapper never had it either).

**`profile.icon_overrides`** is **slots only**, for the same binding reason. Under slots the cell icon is ours, keyed by spell ID, so `layoutBar`'s texture write resolves the override through `Util.ResolveIconOverride` (it outranks the CDM conditional-icon path); under groups Blizzard writes the icon from the secret aura via the bound `SetIcon` and there is no spellID to key on. This was **broken for the whole migration** and fixed 2026-08-17 — the CDM wrapper got overrides for free from `Util.ApplyBarIconOverride` off a viewer child, and the addon-owned cell has no `cooldownInfo`, so the panel was writing entries nothing here read.

**`pandemic_glow`** rides Blizzard's native `AddPandemicRegion` (12.1.0.69111) through `AuraContainer.AttachPandemic` / `SyncPandemic` — no `ShowPandemicStateFrame` hook and no per-spell timing needed, because the engine owns the region's visibility. The overlay anchors to the duration strip rather than the whole item (the host's `.Bar` binding), and the feature works under **both** engines. Blizzard keeps *driving* it while auras are secret, but the addon cannot *reconfigure* it there — the overlay sits inside the button's restricted subtree — so a settings change made in a dungeon is queued and applied when that window ends. Costs: the window is Blizzard's and the remaining-% is unreadable, so the urgency-ramp keys (`pandemic_glow_threshold_high`/`_low`, `_color_mid`, `_color_urgent`, `_urgency_borders`) are **gone** — no widget, no reader, the curve renderer behind them deleted, and swept from the profile defaults; `pandemic_glow_excludes` is slots-only, for the same reason `spell_colors` is: this tracker has no per-spell groups engine, whose stamped `cue_spellID` lets BuffTracker honour the excludes under groups (#47). The Tracking tab hides the pandemic column while a bar section runs groups. The cue is a **static border** on the duration strip — a binary window has nothing to pulse against, and nothing animated can run inside an aura button's subtree — so `pandemic_glow_style` is reduced to the two border variants (outside/inside) and `pandemic_glow_lcg_alpha` is gone too — LibCustomGlow cannot run in that subtree at all. `.context/migration-parity-gaps.md` "Permanently inert settings".
