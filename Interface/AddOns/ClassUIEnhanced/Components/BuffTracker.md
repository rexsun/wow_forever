# BuffTracker

> **The rendering engine lives in `Core/AuraIconTracker.lua`**, a `CreateTracker(config)` factory. This component is the config (which spells, which settings table, which CDM viewer supplies the groups-vs-slots mode); everything described below — containers, both engines, cell chrome, glow syncs, layout, lifecycle — belongs to the factory and is shared with every `buffs`-type Additional Frame. The bar twin is `Core/AuraBarTracker.lua`. They are deliberately two files rather than one parameterized engine: only the *shape* is shared, the icon path places a grid through `IconTracker.PlaceGrid` and the bar path a single-line flow.

Renders tracked aura icons via Blizzard's 12.1 **AuraContainer** (`CustomAuraContainerTemplate`) through the `Core/AuraContainer.lua` facade. CDM category `BuffIcon` is a **data source only** (`Core/CDMDataSource.lua` `BuildComponentSpellMaps`, "BuffIcon" domain — CDM spells minus Additional-Frame-routed ones, plus custom spells; `buildSpellMap` **merges** the helper's two return maps into one, fed to both containers); the Blizzard `BuffIconCooldownViewer` frame is alpha-suppressed and never rendered. Above CooldownTracker by default.

Defaults: 400×100, icon_size 40.

**Containers:** a container has exactly ONE unit, so the tracker uses **three**. Per-group/per-slot `SetUnit` is deferred to **12.1.5**, so this is the architecture for the whole 12.1 cycle rather than a stopgap — see `.context/patterns-auracontainer.md` for the source verification and what to watch for when it lands. `CUE_BT_Container_Aura` (unit player) carries group `"BuffTracker_main"` — filter `"HELPFUL|PLAYER|INCLUDE_NAME_PLATE_ONLY"`. `CUE_BT_TargetContainer_Aura` (unit target) carries `"BuffTracker_target_harmful"` (`"HARMFUL|PLAYER"` — own DoTs). `CUE_BT_TargetHelpfulContainer_Aura` (unit target as well) carries `"BuffTracker_target_helpful"` (`"HELPFUL|PLAYER|INCLUDE_NAME_PLATE_ONLY"` — own buffs on an ally target). The third container exists **only so the helpful block can be hidden on its own** — see "Self-target duplicate" below.

**All three groups are fed the SAME spell map.** There is no self/target split: Blizzard's own CDM watches every tracked spell on both units (`CooldownViewerItemDataMixin:GetAuraData` walks `scanUnits = { "player", "target" }` and takes the first match, `CooldownViewerItemData.lua:1`) and never reads the `selfAura` DB2 flag at all — zero references to it across `Blizzard_CooldownViewer`. Splitting on that flag put a spell in one container and matched it in neither; live case: Fire Breath `357208`, whose target DoT is the linked `357209`, never reached the target container. The filter strings mirror Blizzard's `GetTargetAurasFilterString` (`:661`) — friendly units take HELPFUL **with** `INCLUDE_NAME_PLATE_ONLY`, hostile units take HARMFUL. Blizzard picks one per unit via `UnitIsFriend`; we run both target groups concurrently instead, because `SetAuraGroupCandidateFilters` is combat-restricted and a target-change re-filter would break mid-pull. `CDMDataSource` still *returns* the split because `Core/IconTracker.lua` needs it for an unrelated purpose (gating which spells its player-unit aura slots may bind). A target SWAP fires no container-side refresh (`SetUnit` early-outs on an unchanged token), so `Initialize` registers `PLAYER_TARGET_CHANGED` → `UpdateAllAuras()` on both target containers — Blizzard's sanctioned external refresh hook.

**Self-target duplicate (fixed).** While the player targets themself, a player buff satisfies both the player-HELPFUL group and the target-HELPFUL group and renders twice. Blizzard never hits this: `scanUnits` order gives it one match per spell. A candidate-filter flip on `PLAYER_TARGET_CHANGED` is not available — every container call is combat-restricted, i.e. dead exactly when targets change most — so the target-HELPFUL group was moved into its **own container**, which `syncSelfTargetSuppression()` simply `SetShown(false)`s while `UnitIsUnit("target", "player")`. `SetShown` on an addon-owned frame is unrestricted, and a whole container is the finest granularity available (under groups a button's aura identity is secret). It is chained LAST so hiding it leaves no hole, and hidden children drop out of `GetBoundsRect`, so `resizePair` closes the gap. Called from the target-change handler and once at the end of `Refresh`, since a login or profile switch with the player already self-targeted fires no event.

**Identity-gate guard (same function).** Blizzard applies `includeSpellIDs` only inside `CanApplyIdentityCandidateFilters`, which fails for a HELPFUL aura on a unit that is neither player-controlled nor assistable, and for a HARMFUL one on a unit the player can assist — and when it fails the spell-ID filter is *skipped*, so the container shows everything its filter string admits. `syncSelfTargetSuppression` therefore also `SetShown`s each of the three blocks on whether its own filter's gate holds for its own unit (`AuraContainer.IdentityFilterHolds`): the player block, the target-HARMFUL block on the target *not* being assistable, the target-HELPFUL block on it being assistable. That is the same choice Blizzard's `GetTargetAurasFilterString` makes by reaction — we run both target filters at once only because a candidate-filter flip is combat-restricted, and hiding is the combat-safe way to pick one. It is the only repair for the two target cases, which fail on every evaluation; the player block's gate is unconditional since 12.1.0.69465 and the call is kept only so the mirror stays complete. Re-run on `PLAYER_TARGET_CHANGED` and on `UNIT_FACTION` for the target and the player — reaction can flip with no target change (mind control, a neutral NPC turning), and when the player is the one mind controlled only `"player"` fires.

**Per-spell unit scope (`aura_unit`).** A user setting, orthogonal to the automatic fix above: each tracked spell can be restricted to `"player"` (self buffs only), `"target"` (target debuffs and ally-target buffs), or left at the default `"both"` (all three groups). Stored keyed by the **base** spellID and expanded across the entry's full aura identity set by `AuraContainer.ExpandUnitScope` before use — the map the engines walk contains linked ids, which would otherwise keep the default. The Tracking tab sets it per spell in its **Track On** column (`Core/UI/TrackingTab.md`), keyed on the row's key. Blizzard owns aura membership, per-button updates (UNIT_AURA), and geometry; the addon supplies regions once per pooled button via `AuraContainer.makeInit` (`cue_Icon`, `cue_Count` stack text, `cue_Cooldown` duration spiral + its timer FontString bound with `SetDurationText`), shared by all three groups. All regions are children of the forbidden-object button, `cue_`-prefixed (see `.context/patterns-auracontainer.md`).

**Two engines, one per display mode.** The tracker carries BOTH AuraContainer engines and picks per refresh from `always_show_tracked` (`tracker.IsUsingSlots()`). Until 2026-09-22 it also followed Blizzard's viewer "Hide when inactive" live; `pm.MigrateHideWhenInactive` now copies that setting in once per profile (a `false` reading turns `always_show_tracked` on) and it is never read again.

**Groups is the default.** `always_show_tracked` defaults to `false`, matching Blizzard's own shipped `HideWhenInactive = 1` for every CooldownViewer system (`EditModePresetLayouts.lua:672-741`, honoured only by the buff item templates, `CooldownViewer.xml:161, 212`), so out of the box this tracker runs groups and every slots-only feature below is off. **The Options panel hides what the active engine cannot deliver** — `active_glow` + its color, the whole `proc_glow` suite, `spell_colors` and `overflow_icon_size` are absent (not greyed) while groups is in force, in the trackers tab and on every Additional Frame. The gate is `tracker.IsUsingSlots()`, the same single mode read the layout uses, so panel and layout cannot disagree; toggling "Always Show Tracked Auras" re-renders the panel so the widgets follow. `icon_overrides` is a global profile tab, not per-component, so it is never hidden.

**Per-spell groups are the compacting engine** — one `AddAuraGroup` per spell instead of one for all, each capped at `maxFrameCount = 1`, which keeps compaction *and* restores per-spell identity, because a group filtered to a single spell's identity set can only ever show that spell. `icon_overrides` (via the `ClearIcon` path in `AuraIconTracker.restyleButton`, which drops the `SetIcon` bind for exactly the spells that have an override — a group filtered to an identity set knows the *entry*, not which of its auras is live, so everything else keeps the bind and lets the engine draw the matched aura; see `Core/AuraTrackers.md` "Which spell the icon and name are drawn from"), `active_glow`, `spell_colors`, the CDM visual alert and `priority_order` all become reachable under compaction; the layout-shaped gaps below do **not** come back, since Blizzard still owns the flow and its rect is still secret.

It shipped behind a `per_spell_groups` toggle while experimental and became **unconditional** on 2026-09-09 — there was never a reason to prefer the plain group: identity is strictly extra and the compaction is Blizzard's either way. The toggle and the profile key are gone; the plain-group path survives only as the always-empty branch that keeps one engine holding frames at a time. Ignored while `always_show_tracked` forces slots. Design and the Blizzard source facts: `.context/patterns-auracontainer.md` → "One group PER SPELL".

**`always_show_tracked` is the engine switch** (Options → "Always Show Tracked Auras", default `false` = groups). It makes the slots-only features reachable without touching a Blizzard frame this addon keeps at alpha 0 — the discoverability problem recorded in `.context/migration-parity-gaps.md` "Groups — the degraded engine — is the DEFAULT". Read once per `Refresh`. Turning it on gives up compaction — only groups can compact, since the active set is secret.

| Mode | Engine | Lays out | Owns the icon |
|---|---|---|---|
| Hide-when-inactive (compacting) | `AddAuraGroup` | Blizzard's flow layout | nobody |
| Always-show (static grid) | `AddAuraSlot` ×N | us, via `IconTracker.PlaceGrid` | us — a chrome cell |

This is forced, not a preference: only groups can compact (the active set is secret), and only slots can hold a stable grid (group frames are flow elements and close up). Switching needs no removal API — neither engine has one; the idle engine takes `includeSpellIDs = {}`, which `DoesAuraPassCandidateFilters` fails every aura against, so it holds zero frames.

**A third, experimental mode: the collapsing slot chain** (Options → *Mix Player and Target Auras*, `collapse_layout`, default off, offered only while Always Show is off). It runs the slots engine but chains the slot buttons to each other, spell by spell, with `SetCollapsesLayout`, so inactive ones close up as under groups while player and target auras share one Tracking-tab order. Under groups every target aura follows the whole player block. One line, no wrap, no proc glow; `IsUsingSlots` leaves it out, so the panel shows the groups widget set. Contract in `Core/AuraTrackers.md` "Collapsing slot chain".

**Always-show (slots).** One slot per (spell, container), and **all three slots of a spell share ONE chrome cell** — player-HELPFUL, target-HARMFUL and target-HELPFUL — since a tracked spell may land on the player, as a target debuff, or as an ally-target buff, and only one can match at a time. One shared cell pool is what keeps a spell to a single grid position: with the map now fed to both containers, separate per-unit pools would draw every always-show spell twice. **Role split:** our plain `cell` Frame carries the persistent chrome (`cue_Icon` texture from `C_Spell.GetSpellTexture`, the shared `Util.ApplyIconBorder` edge) and the slot button carries only the aura-driven adornments (`SetApplicationCount`, `SetDurationCooldown`, `SetDurationText`) — deliberately **no `SetIcon` bind**, because anything created on the button inherits the button's `ApplyVisibility` hide, which is right for adornments and fatal for chrome. The button is `SetAllPoints`'d to its cell *inside* `initializeFrame`, which the frame provider runs BEFORE applying access restrictions, so afterwards only the cell is ever moved or sized and the button never needs another (restricted) geometry call. Cells live in one array indexed by position in the sorted spell list; all three containers' `SyncSlots` calls walk that same list through the same `cellForSlot`, so slot `i` on any container lands on cell `i`. That is also why `aura_unit` is applied by neutralizing a slot's `includeSpellIDs` rather than by trimming the list — the cell index IS the list index, so a per-container list would misalign the three sets of buttons. Slots are a retargetable pool: keys are allocated once (`cue_slot_<filter>_<index>`) and repointed via `SetAuraSlotCandidateFilters`, guarded by a per-container spell-order signature because every such call ends in `UpdateAllAuras()`; the scope is folded into that signature via `SyncSlots`' `sigSalt`, since it can change with the spell list untouched.

**Refresh:** rebuilds the spell map, then three `AuraContainer.SyncGroup` calls (each skipped engine-side when the per-group sync signature — sorted spell IDs + layout opts — is unchanged) and, in groups mode, `syncContainerLayout`, which maps the old viewer-layout contract onto the flow layout: `layout_direction` → flow axis, `layout_alignment` → flow origin (left/right/top/bottom exact; **center approximated** by pinning the container's cross-axis center edge point to the wrapper — full lines match old per-row centering, a partial last line stays origin-aligned; every block flows left to right, so the Tracking-tab order reads the same as the slots grid — the 3.0.0 mirrored player block, which put its partial row by the target seam, reversed that order and was removed), `overflow_direction` → cross-axis line growth (old defaults: rows overflow upward, columns rightward), line cap via `SetFlowLayoutMaximumLineSize` from `max_per_row` count or `width`/`height` constrained by the anchor-inherited size (`GetInheritedWidth`/`Height` — the "follow parent %" behavior). The target block is **chained directly onto the end of the player block** along the run axis: `targetContainer:SetPoint(originPt, container, trailingPt, pad, 0)`, where `originPt` is the target's own flow origin and `trailingPt` is the opposite edge of the player container along that axis (`layout_alignment == "right"` / `"bottom"` reverse it, mirroring `applyContainerFlow`'s growth direction). A horizontal layout therefore puts the two sections side by side on one row, a vertical layout continues the column.

**This is an anchor, not an estimate.** `OnLayoutComplete` sizes each container to its own *visible* block, so the seam tracks the live icon count under hide-when-inactive and the blocks abut exactly. The earlier settings-derived offset reserved room for every *tracked* aura and left a large gap whenever most were inactive; `sectionSize` existed only for that and is gone.

**Both containers live inside `CUE_BT_Pair`, a bounds frame that centres the pair as a unit.** Frame hierarchy is `wrapper` → `pairFrame` → the two containers (no per-container wrapper — `AuraContainer.CreateContainer` makes a bare container so nothing contributes a 0×0 rect to the bounds). `pairFrame:ResizeToBoundsRect()` sizes it to the two blocks: the call takes no arguments and returns nothing, so the secret extents are consumed engine-side and never reach Lua. Size comes from the children, position from the single `SetPoint(pinPt, wrapper, pinPt)` — independent, so no circular dependency — which is what makes `layout_alignment = "center"` centre the **pair** rather than either block. Chaining alone could only ever centre the player block, leaving the pair off by half the target block.

Every resize is preceded by `SetSize(0.001, 0.001)`: the bounds rect unions the frame's own rect with its children's, so without collapsing first the frame can only grow and the centring sticks at the widest burst ever rendered. It runs from an `OnUpdate` rather than from `Refresh`, because Blizzard sizes each container from its own update pass and compaction changes the extents whenever an aura comes or goes — including mid-combat, where `Refresh` bails. Slots mode clears that `OnUpdate` and pins `pairFrame` to the wrapper instead; there we own the grid and `PlaceGrid` already centres it exactly. See `.context/patterns-auracontainer.md` "`Frame:ResizeToBoundsRect()`". Element size/spacing come from `icon_size` / `icon_height` / `icon_offset`. AuraContainer API calls are restricted in combat, so `Refresh` bails under lockdown and the combat-exit layout pass (`Core/Anchoring.lua`'s `OnLeaveCombat`, which runs `ContentLayout` = `Refresh`) catches up; the containers keep displaying existing auras internally meanwhile.

**Layout fidelity is engine-dependent.** Under **slots** the grid is entirely ours: cells go through `IconTracker.PlaceGrid`, the same placement the icon trackers use, so the full old-viewer feature set applies — `layout_direction`, per-line `layout_alignment` (a partial last row centers on its OWN count), the `fixed_width` / `fixed_width_spread` / `fixed_width_stretch` modes, `overflow_icon_size` on overflow lines, `overflow_direction`, `min_width`, and the anchor-inherited caps. Under **groups** those remain permanently degraded — per-line counts and row membership are genuinely secret there, so centering is block-level and the fixed-width modes fall back to `max_width` at `icon_size`. Record: `.context/migration-parity-gaps.md` "Groups — the degraded engine — is the DEFAULT".

**Icon order is engine-gated for the same reason.** `priority_order` (Options → Icon Order, see `Components/README.md`) reaches the render under **slots** — `fillSortedList` orders the shared cell list, so the arrangement IS the grid — and under **per-spell groups**, where each spell's group carries its rank as `layoutIndex`. Since per-spell groups became unconditional, both of BuffTracker's engines honour it; the plain single-group path, which Blizzard flows with `AuraContainerSortMethod.Default` and offers no addon-side lever, is no longer reachable here.

**Sizing is engine-gated.** Under **slots** it is content-hugging: `GetWantsContentWidth` mirrors the icon trackers (vertical / `max_per_row` / `max_width` with a set `icon_size`), and `GetComponentSize` returns `IconTracker.ComputeGridGeometry` over the mapped count — the same call the placement used, so estimate and layout cannot disagree. Under **groups** it stays FIXED (decision 2026-07-26): the configured `width`/`height` with a min-width floor and inherited cap, because the container's real rect is secret and a content estimate could only come from the mapped count, over-reserving permanently while looking dynamic to the anchor system; `sectionSize` still sizes the internal wrappers there. Either engine reports 0×0 when collapsed. The fixed box is why a bar tracker (BuffTrackerBars or a `bar` Additional Frame) anchored to this one pins to `tracker.GetBoundsFrame()` — the engine-sized `CUE_BT_Pair` — instead of the box, so it rides the visible buffs (`Components/BuffTrackerBars.md` "Sitting on BuffTracker"). A slots-mode spell-count change also fires `Anchor.OnComponentStateChange` (the box moved), which is rare — talents, spec, CDM config — and never a combat path.

**A summon never fills its row; `show_totems` shows it instead** (Features → *Track Totems*, default off, 2026-09-30). A summon — Dreadstalkers, Demonic Tyrant, a shaman totem — applies no aura, so its CDM entry never matches, in either engine. The key adds one icon per totem **slot**, in line at the head of the run, before the player buffs: under the groups engine a collapsing chain the player block joins, so empty slots close up; under the always-show grid the first cells, so each slot keeps its place. Each icon is piped blind (`haveTotem` → `SetAlphaFromBoolean`, icon → `SetTexture`, `GetTotemDuration` → `SetCooldownFromDurationObject`), an empty slot is `Hide()`n, and `PLAYER_TOTEM_UPDATE` plus the cooldown's own `OnCooldownDone` drive it. The icon twin of BuffTrackerBars' rows; contract in `Core/AuraTrackers.md` "The icon twin".

**Restyle path:** `restyleButton` applies `timer_font` / `stacks_font` (face/size/outline via `framework:SetFont`, color, shadow suppressed when an outline is set), `hide_cd_swipe` / `hide_cd_text` (`SetDrawSwipe` / `SetHideCountdownNumbers` on the button's own `cue_Cooldown` — master applied these by walking the CDM viewer's children, which this engine has no equivalent of; this is what carries a live toggle out of combat, while a new button's swipe is set before the bind by `makeInit` / `initSlotButton`, see `.context/patterns-auracontainer.md`), `reverse_swipe` (`SetReverse(settings.reverse_swipe ~= true)` on the same object — Blizzard's BuffIcon swipe is `reverse="true"`, `CooldownViewer.xml:183`, so unset means reversed and the key flips it; pinned by `tests/cdmparity_check.lua`), `hide_icon` under **groups** (`Util.ApplyIconVisibility` on the button's `cue_Icon`, re-asserted after `ApplyIconBorder` re-shows the border; under **slots** the icon is on the cell and `placeCell` owns it), and `AuraContainer.ApplyTooltip`. Registered with the facade's dirty-flag system (`RegisterTracker` before `makeInit` so acquire-time styling finds it; `MarkDirty` on `OnProfileChanged`; the `private.fontsDirty` Options/EditMode contract is bridged into `MarkDirty` inside `Refresh`; `RestyleIfDirty` walks tracked buttons).

> ⚠️ **A restyle-path key no longer depends on its setter remembering `private.fontsDirty`.** The bridge above is one of *two* things that turn a live edit into a `MarkDirty`: `Refresh` also compares the file's `RESTYLE_KEYS` list against the values it last saw and marks dirty on any move. The flag stays for the font profiles (tables, rebuilt in place), and setters that already raise it are left alone. This closed the `patterns.md` "fontsDirty" trap for good — it had bitten `hide_icon` / `hide_cd_swipe` / `hide_cd_text` here, and `icon_size` / `icon_height` / `bar_height` / `icon_offset_x` / `icon_offset_y` / `collapse` / `show_timer` / `bar_fill_color` across the tracker panels, the Additional Frame panel and EditMode. **Add a new restyle-applied key to `RESTYLE_KEYS`**, not to a setter.

**Feature options this tracker honours: `hide_icon`, `hide_cd_swipe`, `hide_cd_text`, `reverse_swipe` — and nothing else in that family.** The rest (`hide_active_swipe`, `hide_gcd_swipe`, `gcd_edge_charges`, `no_cd_overlay*`, `no_desaturation`, `hide_charge_cd_text`, `hide_zero_charges`, `icon_visibility_mode`) describes an `IconTracker` button's **cooldown** state; an aura button has a duration, not a cooldown, so there is nothing for them to act on. The tracker panel never offered them; the Additional Frame panel did, and now hides them for `buffs` frames.

> **What the pre-migration renderer really drew: Blizzard's BuffIcon, untouched.** Until 2.13.4 both this tracker and a `buffs` frame displayed live BuffIconCooldownViewer children. The Additional Frame pass called `Util.ApplySwipeToChild` only on children carrying `cooldownSwipeColor`, which only Essential/Utility items set (`CooldownViewerCooldownItemMixin`), so no BuffIcon child was ever restyled. That whole feature family, `reverse_swipe` included, never reached a buff icon. What users saw was Blizzard's cooldown: reversed (lit, darkening as the aura runs out), 0.7 black swipe, no edge, aura countdown rounding. Under **slots**, `cue_Cooldown` is created with exactly that (`SetSwipeColor` / `SetDrawEdge(false)` / `SetUseAuraDisplayTime(true)`) and `restyleButton` sets the direction. Under **groups**, `makeInit` sets none of those three, so the button keeps `CooldownFrameTemplate`'s 0.64 swipe and its edge. It turns the edge off only while `hide_cd_swipe` is on, because the edge would otherwise be left drawn on its own. 3.0.0 mapped `reverse_swipe` straight onto `SetReverse`, which flipped every buff swipe until 2026-09-28.
>
> Of that family, only `no_cd_overlay` / `no_cd_overlay_edge_only` and `no_desaturation` have no aura-button meaning: the engine shows an aura button while its aura is up and hides it otherwise, so under groups there is no inactive-but-visible state to dim or desaturate. Under slots the cell is exactly that state, and `desaturate_inactive` ("Desaturate Inactive Auras", slots only, default `false`) greys it — see `Core/AuraTrackers.md` "Desaturated inactive icons".

**Tooltips** are the aura button's own, not `Core/UI/Tooltip.lua` — the button already owns one and knows the secret aura behind it, which our tooltip cannot. `tooltip_mode` / `tooltip_anchor` are mapped onto `SetMouseMotionEnabled` / `SetHideTooltipInCombat` / `SetTooltipAnchorPoint` by `AuraContainer.ApplyTooltip`, so they work in **both** engines. `out_of_combat` needs no combat callbacks (Blizzard re-evaluates per show). See `.context/patterns-auracontainer.md`.

**`active_glow`** works under **both** engines and needs no aura read at all. The border is a region created on the aura button itself (`GlowEffect.CreateActiveBorder`, built lazily by `ApplyActiveGlow` on the first pass that wants it — five separate init paths bind aura buttons, and building it in each is what left three of them without one), so the engine's own show/hide of that button — which happens exactly while its aura is up — is the glow. `AuraContainer.ApplyActiveGlow` only carries the on/off and the colour, on the restyle path. That binding removes three limits the predecessor had: it needed a per-spell key (so it was slots-only), it read `CDMDataSource.GetAuraState` off a CDM viewer child (so it went dark with the CVar off and reported inactive for every **custom** spell, which has no child), and it needed a `UNIT_AURA` driver of its own. All three are gone; the border is built from edge textures rather than a `BackdropTemplate` and starts its pulse at creation, because the button's subtree allows neither `SetBackdrop` nor `SetScript`.

**`profile.icon_overrides`** is **slots only**, for the same binding reason. Under slots the cell icon is ours, keyed by spell ID, so the slot-sync texture pass resolves the override through `Util.ResolveIconOverride` (it outranks the CDM conditional-icon path); under groups Blizzard writes the icon from the secret aura via the bound `SetIcon` and there is no spellID to key on. This was **broken for the whole migration** and fixed 2026-08-17 — the CDM wrapper got overrides for free from `Util.ApplyIconOverride` off a viewer child, and the addon-owned cell has no `cooldownInfo`, so the panel was writing entries nothing here read.

**`proc_glow_*`** is **slots only**, for the same binding reason as `active_glow` — but it needs no CDM bridge: `C_SpellActivationOverlay.IsSpellOverlayed` answers from the spell ID alone. Master got this free from `Util.HookViewerChildren`'s per-child glow hooks; with no viewer hooks left it is rebuilt as `AuraContainer.SyncProcGlow`, which walks every pooled cell (so surplus cells and the idle engine clear) and glows the chrome **cell**. State is queried by OUR spell ID, not the event payload — the payload carries the *overlayed* id and diverges under an override. Driven by `SPELL_ACTIVATION_OVERLAY_GLOW_SHOW`/`_HIDE` on the shared `auraEvents` frame, registered only while the feature can render.

**Visibility:** the wrapper is an ordinary, unprotected frame (measured in combat 2026-09-28: `IsProtected()` false, `Hide()`/`Show()` go through), so it is **not** in `Core/Anchoring.lua`'s `secureComponents`. Anchoring lays it out, shows it and hides it in combat like any other component. When hidden by rules or chain it is `Hide()`n, not parked at alpha 0: a hidden AuraContainer registers no `UNIT_AURA`, and the layout pass that reveals it — in or out of combat — `Show()`s it and triggers Blizzard's full rebuild. `SyncAlpha` is the lightweight alpha-only sync. See `Core/Anchoring.md` "The combat freeze covers the SecureActionButton trackers only" for the mounted-attack bug that the old membership caused.

**Secret rects:** the containers' own width/height are secret (`OnLayoutComplete` sets them via secretwrap) and must never be read or anchored to — the plain `wrapper` is the component/anchor-facing frame in both engines. `IsCollapsed` is both counts zero, with collapse transitions notifying `Anchor.OnComponentStateChange`.

**Custom spells:** merged into BOTH section maps via `CustomSpells.GetSpellMapFor` (no self/target knowledge — the group filter strings decide where an aura can match); `CustomSpells.OnEnable/OnDisable` gate participation. No separate custom-icon frames. An entry whose `unit` is `focus` matches nowhere, since there is no focus container — the Options unit dropdown therefore offers only Player/Target on this component (see `.context/patterns-auracontainer.md` "Per-spell unit scope").

**`pandemic_glow`** rides Blizzard's native `AddPandemicRegion` (12.1.0.69111) through `AuraContainer.AttachPandemic` / `SyncPandemic`: the engine owns the region's visibility, so this is the one per-aura feature here that works under **both** engines and does not go dark while auras are secret. `applyPandemicGlow` walks both cell arrays (slots) and the component's group buttons (groups) on every Refresh, and needs no event driver of its own. It is, however, the one glow here that is **skipped while auras are secret** — its overlay lives inside the aura button's restricted subtree, unlike `active_glow`/`proc_glow`, which ride the chrome cell — so the pass is queued and retried once the dungeon/raid/PvP window ends.
