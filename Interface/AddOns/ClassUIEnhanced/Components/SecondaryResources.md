# SecondaryResources

Horizontal StatusBars for combo points, soul shards, holy power, chi, runes, arcane charges, essence, soul fragments, stagger, vitality, whirlwind charges, sweeping strikes stacks, teachings of the monastery stacks, wild imps, arcane salvo stacks, nearby soul fragments, ironfur, aimed shot charges, Power Word: Radiance charges, skyriding vigor, and the continuous caster resources Maelstrom (Elemental), Astral Power (Balance), and Insanity (Shadow). Per-spec resolution (`GetEnabled()` → false when no secondary).

Resource colors: class color or per-class overrides. Value text positioned via `ApplyFontProfile` using `value_font` anchor_point/offsets. Below CooldownTracker. Defaults: 400×30.

## Rows — how one component drives several resources

The component is built to show **N resources at once**, one per *row*, while the resolver still produces exactly one. Nothing on screen differs from the single-resource build; the machinery is what changed.

- **`getPlayerSecondaryPowerType()` is unchanged and still the only place per-spec toggles and talent gates live.** `getActiveResourceTypes()` sits beside it and turns that single answer into an ordered list — `{ primary }`, or empty when there is none. Extra resources append *after* the primary, so row 1 renders what the single-resource code rendered whenever there is a primary. Each extra is gated on its own setting **here**, not in `getPlayerSecondaryPowerType` (which resolves the primary only) — and its Options setter must call `Refresh()`, not `ReevaluatePowerType()`, because the latter compares only row 1's resource and would early-return without ever adding or removing a row 2. The list is a module-owned scratch table rewritten in place, so the Refresh path allocates nothing.
  **An extra does not need a primary** (since 2026-09-23). With the primary switched off — a Frost Mage with `frost_icicles` off and `mage_shatter_stacks` on — the first extra takes row 1 on its own. Until then the extras block was guarded on `count > 0` and the Shatter row silently never appeared, while its tooltip promised one. Three things make row 1 safe for an extra:
  * **`playerPowerType` is row 1's resource, not the primary.** Every transition path (`ReevaluatePowerType`, `Initialize`, the talent / spec / shapeshift / skyriding handlers) resolves it as `getActiveResourceTypes()[1]`. Resolved from `getPlayerSecondaryPowerType()` it stayed nil, and `GetEnabled()` hid the component.
  * **`Refresh` runs its transition test before the "nothing to show" gate.** An extra's setter calls `Refresh`, and with no primary `playerPowerType` is nil until that transition assigns the extra, so the old `getEnabled()` early return would have swallowed it. The gate ahead of the test is now only `settings.enabled`; `count == 0` hides after it.
  * **`types.hasPrimary` keeps thresholds on their own strip.** `resource_threshold.resource = nil` means "the primary row". An extra standing in row 1 answers to its own `base` only (`isPrimary` is `rowIndex == 1 and hasPrimary`), and the Options picker offers it by `base` rather than nil. Otherwise a threshold set while Icicles is off would move to Icicles when they come back, which is the bleed `resource` exists to prevent.

  In practice only Shatter reaches this: every other extra sits on a spec whose primary has no toggle (Arcane Charges, Soul Shards, Essence, both DH fragment pools). The dedicated per-resource event frames still write to row 1, which is safe because each serves only its own primary, and an extra is never one of them.
  And **the primary need not be the spec's usual one**: while skyriding it is `SKYRIDING_VIGOR`. That used to leave an Arcane Mage flying with the Salvo strip on showing Vigor on row 1 and Salvo on row 2 — every extra's own gate (class, spec, talent, setting) is still true in the air, so each one kept its row. The extras block is guarded on `primary ~= SRC.SKYRIDING_VIGOR`: skyriding takes the whole component, and a class resource has nothing to say while mounted. Guarded once at the block rather than per entry, since the answer is the same for all of them.
- **`rowFrames[i]` is a plain Frame inside `resourcesFrame`; `rows[i]` is its state** — `frames` (the segment pool), `count` (visible segments) and `powerType`. `layoutRows(count)` gives each row its slice: a single row is `SetAllPoints(resourcesFrame)`, several split the cross axis (stacked for a horizontal component, side by side for a vertical one) so a row's own segments still run along the main axis exactly as before. **The component GROWS for an extra row; it does not divide.** `height` is the primary row's, `extra_row_height` (default **8**, a third of `height`'s 25 — the primary keeps the visual priority) is each extra's, and `crossAxisSpan()` — `height + extras × (extra_row_height + gap)` — is what `GetComponentSize` returns on the cross axis. An even split of a fixed 25px was the original behaviour and it was wrong twice over: it halved the primary the moment an extra appeared, and a 4-pip Unbound Flame strip beside 6 Essence segments got equal height but fatter segments, so the extra read as the main bar.

**`layoutRows` publishes each slice as `rows[i].span`, and `layoutBars` sizes segments from that — never from the row's own rect.** `layoutAllRows` re-anchors every row (`ClearAllPoints` + two-point anchors) and then calls `layoutBars` in the same pass, so a row measured there reads back 0; the profile fallback that caught it drew `settings.width`-wide segments inside whatever width the anchor system had actually given the component. Live incident: a zone transition brought CooldownTracker back 400 wide and the Essence strip beneath it kept 450-wide segments — visible only because the last segment is two-point-anchored and alone tracked the real edge (four at 88.7, a fifth at 36.1). So the main axis comes from `resourcesFrame`, whose rect that pass does not touch, the cross axis from `span` (nil at one row, which IS the component frame), and `settings.width`/`height` answer only at cold start, before the component's own anchors have resolved. This is the same rule `layoutPips` already follows for pip geometry, one level down. Guarded by `tests/rowspan_check.lua`.

`layoutRows` applies the two settings as **weights against the frame's real cross size**, not as pixel sizes. The anchor system can drive that axis (a left/right-side dependent inherits its parent's height), and a literal `SetHeight(settings.height)` would overflow or underfill it; proportional means the rows always fill the frame exactly, and land on the configured pixel values whenever the frame is the size `crossAxisSpan` asked for. Both weights are clamped to ≥ 1 so a zeroed setting cannot divide by zero.

Because the row count now feeds `GetComponentSize`, `syncRows` fires `Anchor.OnComponentStateChange()` when it changes — gated on the transition, never per Refresh (`.context/performance.md`).
- **`withRow(index, fn)` is the whole trick.** The per-resource logic reads `resourceFrames`, `activeResourceCount`, `playerPowerType` and `rowFrame` as file locals; `withRow` re-points those at a row, runs `fn`, writes the count back into the row and re-aims at whatever row was active on entry. That is what lets ~170 unchanged call sites run once per row. The body is **not** wrapped in `pcall` — a throw inside it skips the restore and leaves every later pass on the wrong row for the session, the failure shape `.context/patterns.md` records for `private.isEditMode` / `private.fontsDirty`. That is accepted: the addon does not catch its own errors, so a throwing row reports as itself rather than as a silently mis-aimed module. The entry row's table is still captured before the body runs and handed back to `aimAtRow`, which takes it as an argument and therefore has no presence check that could turn the restore into a silent no-op on the normal path.
- **Row 1 IS the module-level view, not a copy of it.** `ensureRow(1)` adopts the existing `resourceFrames` table, count and power type rather than starting empty, and outside any pass the pointers are aimed at row 1. Everything that was never routed through `withRow` — the `OnUpdate` scripts, the option setters, `GetEnabled`, the anchor system's queries — keeps reading the primary resource's state exactly as before.
- **Per-row passes.** `Refresh` calls `syncRows(types, count)`, then `withRow(i, refreshRow)` for each row, then `applyPowerEventRegistrations()` once; `refreshRow` is the old Refresh tail verbatim (decide events → `refreshResourceCount` → the per-resource display branch → `applyColors` → `cdgState.updateDisplay` → the value-font pass → `updateValueText`). The component's Show/Hide gate is the sum of the rows' counts. `layoutAllRows` is the `OnSizeChanged` handler and re-runs `layoutBars` per row; it skips `layoutRows` at one row, which needs no recompute because it is anchored to all four sides.
- **A resource change is a transition, and `Refresh` refuses to absorb one.** Right after the `settings.enabled` gate, `Refresh` compares row 1's resolved resource (`types[1]`) against the cached `playerPowerType` and hands a mismatch to `ReevaluatePowerType`, then returns. Without that, `syncRows` would write the new type into row 1 and `withRow` would publish it into `playerPowerType` silently, skipping the teardown that unregisters the *outgoing* resource's events and clears its pip strip — reachable from a profile apply, which refreshes every component. `ReevaluatePowerType` assigns the new type before calling back into `Refresh`, so the re-entrant pass finds them equal and proceeds; the recursion is bounded at one level. The test runs even while `playerPowerType` is nil, so a `Refresh` from an extra's setter can bring the component up from nothing.
- **Row teardown.** `syncRows` releases every row past the new count, and only the rows that were actually active — `rowFrames` never shrinks, so walking it would re-release the session's whole row history on every Refresh, in combat. The pool is kept (frames are pooled, never destroyed) but each segment, the row's value text and the row's pip strips (`"sweepingstrikes"` / `"teachings"` / `"wildimps"` / `"cdg"` / `"shatter"` / `"arcanesalvo"` / `"nearbysouls"`) are hidden and the count zeroed, so a spec change from two resources to one strands nothing. The strips need releasing explicitly because their containers are parented to `resourcesFrame`, not to the row, so hiding the row does not reach them; they are hidden rather than rebuilt, since the tap constructors no-op in combat and while auras are secret.
- **Per-row value text.** The centered `valueText` moved off the component frame onto the row container (`rowFrame.valueText`, on a row-owned overlay at the same absolute frame level and draw layer as before), so each row can show its own number. `updateValueText`, the vigor speed readout, the Ignore Pain / stack-strip suppressions and the value-font pass all read the current row's.
- **`VALUE_TEXT` is the value-text dispatch**, keyed by resource token, one closure per resource that is a pure read of file-scope state. It replaced a seventeen-deep `elseif` chain whose `else` fallthrough — plain `UnitPower`, the common case for most specs — paid every comparison on a per-power-event path. Four cases deliberately stay as branches after the lookup, because a row cannot express what they do: **SoulShards** reads the per-call `settings`; **Ignore Pain** and the **stack strips** write no value at all, leaving the bound FontString's text alone (neither writing nor hiding); **Vigor** reads `settings` too and *hides* in speed mode. Widening the row contract to cover them — a second return, or passing `valueText` in — would cost more than the branches it removed.

  > ⚠️ **The table must stay directly above `updateValueText`, below every local it reads.** Each row is a closure and Lua 5.1 captures at definition time, so a row hoisted above (say) `cachedStaggerPct` captures nil, reads as a global forever, and prints `0%` with no error anywhere — the silent captured-nil VALUE case in `.context/patterns.md`. Unlike `STACK_STRIPS` (constructed from `SRC.*` constants, so position-independent), this table is position-dependent by construction. The `GETGLOBAL` bytecode scan is what catches a violation; diff review will not.
- **Row-scoped tap keys.** An `auraTap` key names a slot set globally — it is both the `auraTap.pipSets` index and part of the container's frame name — so `tapKeyForRow(base, index)` suffixes the row index for rows ≥ 2 and leaves row 1 with the bare `"sweepingstrikes"` / `"teachings"` / `"shatter"` / `"wildimps"` / `"arcanesalvo"` / `"nearbysouls"` / `"cdg"`. Keys are memoized per (base, row), so the Refresh path stays allocation-free. Whole-component teardowns (`hideStackPips`, `unregisterCdGEvents`) clear every row's key; `releaseRow` clears only the leaving row's. `hideStackPips` must name **every** strip base `stackPipSpec` can produce — its loop is the only thing that reaches a strip on the `OnDisable` / `ReevaluatePowerType` / talent / spec-change / shapeshift paths, none of which run `releaseRow`. The sixth transition path, skyriding, does not call `hideStackPips` at all — a pre-existing divergence, so a strip left up across a mount/dismount power-type change is hidden by the following `Refresh` rather than by teardown.

**Known limits of the current step, for whoever adds the second resource:**

- **Event registration is a union, decided per row and applied once; per-resource event frames are not routed.** `registerPowerEvents` runs once per row, so `powerEventFrame` ends up holding the union, and its handler offers every event to every row in turn (the branch chain self-selects on `playerPowerType`, so a row that does not own the event does nothing — `RUNE_POWER_UPDATE` self-selects too, since `runeState.refreshValues` has no internal guard). Re-registering an event on a frame is a no-op, so passes cannot duplicate; leftovers are cleared as before, by the `powerEventFrame:UnregisterAllEvents()` in each power-type transition handler. **The union is only additive-safe while no two rows register the same event by different means** — `RegisterEvent` and `RegisterUnitEvent` are not commutative, the second call replacing the first's unit filtering rather than widening it. No two branches overlap that way today; a new resource sharing an event with an existing one must use the same registration form.
  The four sub-registrations that carry an else-position *unregister* (the Paladin swing timer, the Coup de Grâce strip, and the spend/builder prediction frames) are the one non-additive part, so they are **decided, not applied**, inside the per-row pass: each row records what it wants in `powerEventWants`, and `applyPowerEventRegistrations()` applies the result once after the loop. A register wins over another row's non-register, and an unregister fires only when no active row asked for it. Nothing is applied at all unless some active row took the static-resource branch — the only branch that decided any of this before the rework — so a lone Essence or Rune row still leaves all four untouched. The wants table is seeded with all five keys and only ever reassigned, never nilled, so the Refresh path allocates nothing.
  The **dedicated** frames those branches delegate to (Whirlwind, Tip of the Spear, Icicles, Ironfur, Maelstrom Weapon, Vitality, the swing timer, the two prediction frames, the Essence Burst tick) still write through the module-level pointers, i.e. row 1 — correct for every resource they serve today, since each is a whole-spec secondary and therefore the primary. Putting one of them in a non-primary row means running its handler body under `withRow` on the row whose `rows[i].powerType` matches.
- **`resourcesFrame:SetScript("OnUpdate", ...)` is component-wide.** The Runes / Essence / Vigor / Ironfur / Whirlwind fills each claim it from inside their row's pass, so only one OnUpdate-driven resource can be on screen at a time.
- **Overlays parented to the component frame, not the row.** The pip containers, the three recharge clip frames and the Icicles glow all hang off `resourcesFrame`, so hiding a row does not take them with it — `releaseRow` hides them explicitly, and `hideRowOverlays` keys the recharge/glow half off the *leaving row's own* resource so releasing an extra row cannot blank an overlay the primary is still showing. Anything new that parents to the component frame rather than the row must be released there too.
- **Singleton overlay state.** `ipState`, `cdgState.pips`, the Fire Blast / Aimed Shot / Radiance recharge bars and `essencePred` are one instance each and attach to whichever row's segments the pass hands them. Row-scoping them is a separate step from row-scoping their tap keys. Three are now done: `reapFc` (row 1), the breakpoint-pip host (row 1), and `stackTap` (whichever row owns the strip, stamped as `stackTap.rowIndex`). The rest are still unscoped and safe only because no spec pairs them with an extra row — check that before adding one.
- **The bound count FontString still gets an explicit hide.** This *used* to be load-bearing because `auraTap.ensure` builds one shared `CUE_SR_AuraTap` container on **`UIParent`** — deliberately, since a bound FS cannot live under a frame we hide — so `releaseRow`, `hideStackPips`, `resourcesFrame:Hide()` and `OnDisable` all missed `stackTap.text`. Since the stack readout moved onto each strip's own pip container (parented to `resourcesFrame`), those hides *do* reach it, and `stackTap.setShown` remains for the two cases container visibility does not cover: `noReadout`, where the pips are wanted and the number is not, and **Show Value off**, which governs this readout exactly as it governs the addon-owned `valueText`. The Show Value gate has to sit here and not on `ensurePips`' `wantCount`: `wantCount` only takes effect in the build branch, and the reuse guard compares `n` and `maxApplications` only, so folding the setting in would leave the toggle waiting for a cap flip or a `/reload`. `setShown` writes an already-bound FontString, so it converges on the next pass. The shared `UIParent` container is still what `reapFc`'s `"soulfrags"` suffix uses, so the caveat is live for that one: `auraTap.syncAlpha` mirrors `resourcesFrame` onto it — `IsVisible()` and alpha, hooked on its `OnShow` / `OnHide` / `SetAlpha` and run when the container is created — so a visibility mode, hide rule, parent-chain hide or fade reaches the count as it reaches the bar. Alpha rather than a hide on the bound FontString, which is write-blocked while auras are secret. Until 2026-09-22 only `OnDisable` faded it (and `OnEnable` forced it back to 1), so a bar hidden by a rule left the count floating where it had been. `OnDisable` also stops `reapFc.capPoll`, whose ticker otherwise only stops itself through `reapFc.update()`. The comment this replaced argued the engine covered it because the aura "cannot be up on a spec that does not have it": true of the two *primary* stack strips, false of the four opt-in ones, which are scoped by **setting** — the aura is still up when the setting goes off. On Vengeance in particular the nearby-fragments aura is up almost continuously.
- **`reapFc` is singleton state OWNED BY ROW 1, and that ownership is now enforced.** All three of its writers on the per-row path — `refreshResourceCount`'s opening `reapFc.hideAll()`, `updateValueText`'s tap-FS pre-block (`tapStacks:SetShown` + `applyTapAnchors`), and `refreshRow`'s fonts pass (`tapFontDirty` + the `seamApplied` clear) — are each guarded on `rowIndex == 1`. Unguarded they were the hide-then-correct defect `.context/patterns.md` catalogues: row 1 hid the overlays and re-showed them through the Devourer branch, then row 2 hid them again and never re-showed, and row 2's `applyTapAnchors(false)` cleared the `seamApplied` flag row 1 had just set, flip-flopping the seam every pass. The guard is sound because **Devourer can only ever be row 1**: `SRC.SOUL_FRAG_DEVOURER` appears solely in `SRC.specSecondaryPower`, so it is always the primary, and extras append after the primary. A non-Devourer character keeps the genuine teardown, because its row 1 evaluates `devourerText` false and runs it.
  The fonts-pass writer was the last one closed, and it was **not** benign: guarding the other two turned its flip-flop into a *sticky* mis-anchor. Row 2's fonts pass cleared `seamApplied` after row 1 had re-derived the seam, and with `updateValueText` now row-1-guarded nothing re-set it, so the pass ended with the flag false while row 1's `valueText` sat at the seam position — and `applyTapAnchors`' restore is gated on that flag, so the next `applyTapAnchors(false)` skipped it and the anchor stayed wrong until the following fonts pass. Before the guards, row 2's own unguarded `applyTapAnchors(false)` had been repairing it by accident. **Lesson: when you guard one writer of shared state, enumerate them all — an unguarded one may be silently compensating.**
  `applyStackTapFont` was the last writer of this shape and is now guarded too, on `stackTap.rowIndex` rather than on row 1 — the readout-bearing strip is usually the *extra* row, not the primary. "It owns a different singleton" was the old justification and it is not a sufficient one: ownership says which object is written, not which row wins when several passes write it. Unguarded it was last-writer-wins, correct only because rows run ascending. `ipState.applyTapFont` genuinely does remain per-row; Ignore Pain is Protection-only and has no extra row, so it has no second writer to lose to.
- **The Devourer text seam is one frame again.** `reapFc.applyTapAnchors` anchors both halves — our own `valueText` and the bound tap FontString — to the row's `rowFrame`. It used to leave the bound half on `resourcesFrame`, which was indistinguishable at one row (`layoutRows(1)` is `SetAllPoints`) but would put the nearby count on the boundary *between* rows at two. The move is legal because the anchor target is not part of the bind: the FS is created on and parented to the aura slot button, which is what `ValidateInboundScriptObject` checks, and "bound FS → plain Frame" is the shape the topology note under "12.1 aura lockdown" calls proven — `rowFrame` is a plain addon-owned `CreateFrame("Frame", nil, resourcesFrame)`. `applyStackTapFont` had already made exactly this move for the other bound readout. **Static reasoning only — not yet seen in game.**

## General resource handling

- **Runes:** fill animation via `OnUpdate`.
- **Essence:** four-case anchoring.
- **Combo points on WoW Forever and every classic client** are per target, as in vanilla. Every whole-unit static read goes through `SRC.staticPower`, which uses `GetComboPoints("player", "target")` there (the same call Blizzard's combo frame makes) and `UnitPower` on retail. Retail must stay on `UnitPower`: its `GetComboPoints` reads 0 with no hostile target. The switch is `SRC.comboPointsOnTarget`, which probes the way Blizzard decides it: only retail loads the player-side `RogueComboPointBar`, so `RogueComboPointBarFrame == nil` means points on the target. No API exposes the rule. Only there are `PLAYER_TARGET_CHANGED` and, where it exists, `COMBO_TARGET_CHANGED` registered (classic's combo frame redraws on both); both re-run `updateResourceValues`.
- **Spec index on a client with no spec system.** Forever answers `GetSpecialization()`, likely always with 1 (the dual-spec group is `GetActiveSpecGroup()`), which is not a retail spec index, so keyed straight into `SRC.specSecondaryPower` it drew an empty Elemental Maelstrom bar on every shaman. `getPlayerSecondaryPowerType` and the mage/warlock/evoker extras in `getActiveResourceTypes` read the index only when `GetNumSpecializations() > 1` — the same test as `PrimaryResources`' `getRealSpecIndex` — and otherwise fall through to `SRC.classSecondaryPower`. A class-level fallback keeps Cat Form combo points (`druid_cat_form`) for a druid with no spec to key on, which also covers retail's initial spec. A second one gives a shaman with no spec to key on the Maelstrom Weapon strip when its talent is known ([below](#enhancement-shaman--maelstrom-weapon)). The per-render spec reads (DK rune colours, build prediction, threshold keys) still take the raw index; none of them decides whether anything shows.
- **A power type with no maximum is no resource.** `getActiveResourceTypes` drops a numeric (`Enum.PowerType`) primary whose `UnitPowerMax("player", …)` is 0 — a Forever class without it, a level below the one that unlocks it. It resolves away rather than drawing zero segments because only a nil `playerPowerType` makes `GetEnabled()` false, and Anchoring skips a disabled component in the chain; an enabled one with nothing to draw is still shown, sized and anchored to. The discrete bars always drew nothing at max 0, but the continuous bars (Maelstrom, Astral Power, Insanity) hard-code one segment and drew an empty fill. String sentinels (charges, stack strips, Stagger, Vigor) are not max-gated; they gate on their own talent or setting. With nothing resolved no power event is registered, so `talentEventFrame` also takes `UNIT_MAXPOWER` for the player (both registration lists, `Initialize` and `OnEnable`) and hands it to `ReevaluatePowerType`, which is a no-op unless the answer changed — the way back when a max appears, and the teardown when the resolved one drops to 0. `UnitPowerMax` is not secret for the player (`.context/patterns-secrets.md`).

## 12.1 aura lockdown (`auraTap`)

12.1 makes instance-ID `C_UnitAuras` APIs Lua-error from addon code while auras are secret (combat/encounters/M+/PvP) — see `.context/patterns-secrets.md` "12.1 Aura Lockdown". All instance-ID reads in this file route through the file-local `auraTap` table (defined after `reapFc`):

- `auraTap.blocked()` — the runtime gate: `C_Secrets.ShouldAurasBeSecret()`. `ShouldAurasBeSecret` is argument-free, returns a plain bool and is callable from tainted code (per `SecretPredicateAPIDocumentation.lua` — note the doc's system Name is "SecretUtil" but `Namespace = "C_Secrets"` is the actual global); the tap uses no `pcall` — it is written to be unreachable while blocked, not to catch. Nothing upstream catches either, so a throw in tap work reached from a per-row pass aborts the Refresh.
- `auraTap.ensure(slotKey, spellIDMap, configureFn)` — lazily creates a 1×1 `CustomAuraContainerTemplate` container (visible, HIGH strata — the Custom button template is a blank shell, so nothing renders except bound elements) plus an `AddAuraSlot` whose button binds a FontString via `SetApplicationCount`; Blizzard's secure path writes the stack count into it as secret text and the engine renders it. **The FontString must be created ON the button** — the bind validates "must inherit all forbidden parent aspects from owner" (`Blizzard_CustomAuraButton.lua:25`, live-verified); positioning happens via cross-frame anchoring instead (a region renders at its anchor target regardless of its parent's position). `configureFn(fs)` runs pre-bind for font/anchor/color (the bind pushes text immediately; font-less `SetText` errors "Font not set"). No-op in combat (container creation errors there by design). `initializeFrame` runs once at slot-frame creation (slots use a dedicated `batchSize = 1` provider), before Blizzard applies `DenyTaintedAccessWhenAurasAreSecret` (`Blizzard_AuraContainerFrameProviders.lua:70-79`) — but under **`UntrustedLayoutScriptExecution`**: any `SetPoint` inside it errors ("Anchoring disallowed as dependent object would inherit forbidden aspects", live-verified). Create + set font object + bind ONLY there; `configureFn` (styling/anchoring) runs after `AddAuraSlot` returns — synchronous, so the bound FS is available immediately, in plain execution context.
- `auraTap.ensureBar(slotKey, spellIDMap, parent, maxApplications, configureFn)` — the `SetApplicationBar` analog of `ensure` (API shipped on PTR, see `.context/patterns-auracontainer.md` "SetApplicationBar"). Creates a DEDICATED container (parent chosen by the caller — pass a clip frame for overflow masking) + slot whose button binds an addon-created StatusBar; Blizzard drives min/max/value engine-side (`maxApplications` is MANDATORY — nil Lua-errors in the first display update). Geometry model: slot buttons are NOT in the container flow layout (groups only), so the button has no rect until the caller anchors/sizes it — legal out of combat under `DenyTaintedAccessWhenAurasAreSecret`. The bar is created on the button pre-bind (no anchors — `UntrustedLayoutScriptExecution`), then `SetAllPoints(button)` after the synchronous `AddAuraSlot` return. The button self-hides while no matching aura is active (`ApplyVisibility`, secret Shown) — the bar vanishes with it. **A live re-bind is impossible** — the bind makes the bound bar access-constrained and `GetValidatedForbiddenObjectTable` rejects constrained objects on any later `SetApplicationBar` (live-verified); a max change therefore requires RELEASING the slot (hide + disable container, clear registry) so the next ensure pass re-creates it — which callers avoid entirely by binding a fixed max and applying any live scale with a clip frame instead (see `reapFc.updateTapAmmo`).
- `auraTap.ensureGlow(slotKey, spellIDMap, target, color)` / `auraTap.setGlowEnabled(slotKey, enabled)` — the **unbound** variant, and the cheapest of the three because it binds nothing. A dedicated container + slot whose button is `SetAllPoints(target)` and carries a plain `BackdropTemplate` border child. The engine Show/Hides the slot button per aura presence (`ApplyVisibility` → `SetShown(secretwrap(auraData ~= nil))`), and an unbound child frame renders exactly while the button is shown — so the border tracks the aura with **zero addon reads**, which is what makes it survive the secret-aura lockdown where a CDM `child:IsShown()` scan cannot. Same shape as `ebonMightTap.glow` in `Components/PrimaryResources.lua`. Constraints: **border only, no `bgFile`** (the tap draws at its own container's strata, above the target's fill and text, so a filled overlay masks them); `button:SetAllPoints(target)` is the ONE cross-frame edge and a LIVE anchor, so it tracks target resizes with no further writes; the border is created **after** `AddAuraSlot` returns (`SetPoint`/`SetBackdrop` inside `initializeFrame` error under `UntrustedLayoutScriptExecution`). Colour is the only mutable part and re-converges on every call. `setGlowEnabled` toggles the *container* — a plain addon frame, so it is combat-safe and is the addon-side gate for setting/spec/power-type; the button's own Show/Hide stays the engine's.
- `auraTap.ensurePips(key, spellIDMap, n, parent, configureFn, unit, filter, maxApplications, wantCount)` / `auraTap.layoutPips(key, hostFn, w, h, vertical)` / `auraTap.stylePips` / `auraTap.setPipsShown` — the **discrete-pip** form of `ensureBar`, and what unblocked the three stack strips. One dedicated container holds N slots, one per pip, each binding its own StatusBar at the SAME `maxApplications`, which defaults to `n`. `ApplyApplicationBar` hard-sets `SetMinMaxValues(0, max)` + `SetValue(applications)` on every update, so the old per-pip `SetMinMaxValues(i-1, i)` window cannot survive a bind — but it does not have to: the engine fills every bar to `applications / maxApplications` of **its own length**, so with the default a bar made `n` pips long and clipped to pip *i*'s rect shows exactly the slice `[i-1, i]`. That is algebraically the same decomposition (verified against the old formula across pip counts, pip widths and half-stack values), with the addon-side read removed. **`maxApplications` is a separate argument so segmentation can be switched off without a second renderer:** at `n = 1` with `maxApplications` still the aura's cap, the same geometry collapses to one host-sized bar filled to `stacks / cap` — a continuous fill through this identical plumbing, with no branch in `layoutPips` / `stylePips` / `setPipsShown` (see "Stack strips — segmented or continuous"). N slots on ONE container is safe and cheap: `AuraContainerAuraSlotManagerMixin:AddAura` walks every slot independently (`Blizzard_AuraContainerSlots.lua`), so N slots may all match the same aura, and slots sharing a filter string share a single aura parse — an 18-pip Arms strip costs one parse, not eighteen. The clip frame sits BETWEEN button and bar: `ValidateInboundScriptObject` accepts any *descendant* of the owner ("must be a direct child or indirect descendent", `Blizzard_AuraContainerUtil.lua:265`), not only a direct child. Layout is split off because pip size comes from the host frames: `layoutPips` takes the pip's `w`/`h` from `layoutBars` rather than reading them back (the last segment in a strip is two-point-anchored, so its `GetWidth` is stale in the same frame), and the virtual strip is `n` pips long with NO gaps — spanning the real strip instead would put boundary *i* one gap-width to the right of pip *i*'s edge. `unit`/`filter` default to `"player"`/`"HELPFUL"`, which is every strip but Shatter; a strip on another unit passes both (see "Frost Mage — Shatter"). `configureFn` is called as `configureFn(bar, i)` — the pip index is what Tier C threshold colors key off. `wantCount` adds ONE further slot beyond the `n` pips, bearing the count FontString (`set.countText`); it is not in `set.buttons`, so `layoutPips` never positions it and the caller anchors the FS itself. `layoutPips` does set its **frame level** (`set.countBtn`, container + 5): a pip's fill is three levels above the container (button > clip > bar) while the count slot is a bare child at container + 1, so the number rendered behind the bars until it was raised. A change to **either** `n` or `maxApplications` RELEASES the set, under the same no-re-bind contract, and both are in the guard for a reason: with segmentation off `n` is pinned at 1 while the cap still moves (Improved Sweeping Strikes flips 12 ⇄ 18), so an `n`-only guard would leave the bar scaled to the old cap for the rest of the session. `updateStackPips` carries the identical two-field pre-check, so the hot path builds no closure on a pass that would not rebuild. A fresh build calls `layoutBars()` once so the strip is not blank until the next resize; `layoutBars` never builds, so that cannot re-enter.
- **Read-back is DEAD (live-verified 2026-07-21):** the access restriction cascades to bound regions, including ones we created — `GetText()` (and any other access: `SetShown`, `SetFont`) on the bound FontString errors in combat. The tap is **display-only composition**: Blizzard writes, the engine renders, addon code touches the bound FS only while `not auraTap.blocked()`.

Tap consumers: the Devourer souls-nearby count (`"soulfrags"` FS slot) and the Devourer ammo bar (`"reapammo"` bar slot, see the Reap forecast section), both on `reapFc.sfIds`. The forbidden-aspect errors only ever hit **out-of-family dependents** (frames anchored ONTO the FS, e.g. a spanning wrapper — `Frame:SetPoint()` in both live traces); never create those, and never re-anchor the FS post-bind. The bound half used to anchor to `resourcesFrame` instead, which was indistinguishable while one row was the only configuration that existed (`layoutRows(1)` is `SetAllPoints`); at two rows that frame's centre is the boundary between them. What is load-bearing is the anchor **shape**, not the particular target frame — the bind validates the FS's *parent* (the aura slot button it was created on), and `rowFrame` is a plain addon-owned `CreateFrame("Frame", nil, resourcesFrame)` exactly as `resourcesFrame` is; `applyStackTapFont` anchors the other bound readout to `rowFrame` already. **FS → plain Frame is the only proven-legal anchor shape for the bound FS** — font-to-font edges, frames anchored ONTO the FS (wrapper span, even pre-bind), and any anchoring inside `initializeFrame` all throw the forbidden-aspect error (all live-verified). Seam derives from profile constants each apply (never live `GetPoint` — no offset compounding); `valueText` writes are ungated (combat-safe — the Void-Meta fix); the FS write is gated on non-secret and `seamApplied` is set only once BOTH sides are placed, so a blocked FS write retries next tick; `active=false` restores the profile anchor; the fonts pass clears `seamApplied`. The button plays no layout role. Fonts via `reapFc.applyTapFont` (profile minus `anchor_point`, `JustifyH LEFT`), re-run via `tapFontDirty` on the first non-secret tick after a blocked fonts pass. ## Evoker Essence Burst overlay

Two independent toggles share the `essenceBurstCost` value (kept in sync with talents and Imminent Destruction) and occupy the same leftmost-N slots so they always coincide.

1. `evoker_essence_burst` (default on) — **Essence Burst tint**: when the Essence Burst aura is active, slots 1..N shift to `evoker_essence_burst_color`; outside the buff they revert to the resource color.
2. `evoker_essence_prediction` (default off) — **Spender-prediction indicator**: a persistent inner ring on slots 1..N showing what the next spender will consume; always visible (independent of EB aura state), so the player can see the spender cost at a glance and the burst tint lights up the same bars when EB procs.

The indicator is four ColorTexture edges parented to the resource frame, flush-anchored and extending 3px inward so the band sits entirely inside the bar; its frame level (+3) is above the burst tap fill (+2) and below the configurable bar border's frame level (+5), so any user-enabled bar border overlays the indicator on pixel overlap — the prediction ring sits underneath, never replaces it. Indicator frames are lazy per-resource-frame (`essencePred.borders`) and reused across refreshes, so the regen-tick `OnUpdate` path is allocation-free. Color is shared with `evoker_essence_burst_color`.

### The tint is engine-driven (parity item K5)

The CooldownViewer scan is **gone**, along with the `/cue ebtap` switch that briefly carried both implementations side by side. What follows is the only path.

**Aura tap.** Nothing is read. `ebTap.apply` builds one `auraTap.ensureFill` container **per slot** (`"essenceburst_<i>"`, `ebTap.maxSlots = 3` — the highest spender cost across specs), each an AuraContainer holding a single `AddAuraSlot` button anchored over `resourceFrames[i]` with an unbound `ColorTexture` child. The engine `SetShown`s the button per Essence Burst presence; the addon `SetShown`s the container per `i <= essenceBurstCost`. Rendered = both.

One container per slot is forced, not a choice: Blizzard stamps `ScriptObjectAccessRestriction.DenyTaintedAccessWhenAurasAreSecret` on the slot button post-creation (`Blizzard_AuraContainerFrameProviders.lua:85`) and forbidden aspects propagate down the hierarchy, so nothing below the button is writable in combat. The container is a plain addon frame and is — and the cost window moves in combat (Imminent Destruction), so the gate has to be live. One container carries one gate.

**Three containers total, not three per spec.** A spec change re-points the existing slots via `auraTap.setSlotFilter` → `SetAuraSlotCandidateFilters`, deduped on `ebTap.filterSpec` because every such call ends in a full `UpdateAllAuras()`. `resourceFrames` is append-only, so the parent frame of each container is stable for the session and the containers outlive any number of spec swaps. An earlier revision keyed containers by spec and hid the outgoing set, on the belief that candidate-filter calls were combat-restricted — they are not, and `.context/api.md` "Aura rules" now records both the correction and what the wrong claim cost.

Cost comes straight from `C_Spell.GetSpellPowerCost` (`querySpenderEssenceCost`), which already folds in talents and the live ID reduction. It returns 0 while EB is active (the spender is free), so `ebTap.cost` holds the last non-zero result — the cost as of EB start, i.e. what the pending spender would have cost. `augID.tracker` registers `UNIT_AURA` (player-filtered) purely as a re-query tick; the payload is unused and secret, and `markDirty` coalesces it to at most one query per frame.

Two behaviours were **given up** to get here, both consequences of never holding the boolean, and both were accepted when the scan was deleted:

- **The charging-bar shift is gone.** The scan held `essenceBurstActive`, which force-filled slots beyond `current` and moved the charging bar to `cost + 1` during EB. Nothing can set that flag any more, so it and `burstShift` were deleted with the scan: the bar stays at its true slot and the overlay covers it while it sits inside the block. The solid fill reproduces the force-filled *look*; the visible partial regen during EB is the loss.
- **An ID transition *inside* an EB window is missed** (one slot too many or too few until EB drops). Nothing recovers it — ID's aura is secret in combat, and the viewer scan was exactly what used to reconstruct it.

What the deletion removed, for anyone tracing it back: `refreshEssenceBurstState`'s BuffIcon scan (`findBuffChildShown`) and its alert-glow fallback on the CooldownEssential/CooldownUtility spender icons (`findSpenderGlowActive`); the permanent `OnUnitAura` viewer hooks (`installEssenceBurstHooks`, `essenceBurstHooked`); the `ESSENCE_BURST_SPENDERS` table; the ID reconstruction in `updateEssenceBurstCost` and `refreshEssenceBaseCost`; `essenceBurstActive` and both `burstShift` sites; and the `/cue ebtap` switch with `db.global.essence_burst_tap`. `applyEssenceBurstColors` survives as the reset half only — nothing else repaints Essence slots, and the tint is now the overlay.

`ESSENCE_BURST_BUFF` stays: it is the candidate filter `ebTap.ids` is built from, which is how the engine knows which aura to show a slot for.

## Stack strips — segmented or continuous

Eight resources are **stack strips**: Sweeping Strikes, Teachings of the Monastery, Shatter (Freezing), Wild Imps, Arcane Salvo, Unbound Flame, the Demon Hunter nearby Soul Fragments and Art of the Glaive. All eight render one secret `applications` count through `auraTap.ensurePips`, are dispatched from `stackPipSpec`, and share `updateStackPips` / `layoutStackPips` / `emptyStackHosts`. `stack_strip_segmented` (default **on**) governs all eight together — there is no per-resource variant.

### Threshold colors on stack strips (Tier C)

Threshold colors have three tiers, and a strip is the third:

| tier | resources | how |
|---|---|---|
| A | public counts (Icicles, Arcane Charges, Combo Points, runes, …) | `applyThresholdColors` — reads the count, honours all three modes |
| B | charge-secret (Fire Blast, Aimed Shot, Radiance, Vengeance fragments) | `applyThresholdColorsSecret` — folds a secret bool through `C_CurveUtil.EvaluateColorFromBoolean`, `"all"` mode only |
| C | the eight stack strips | `stackThresholdColor` — no count at all, colors pip `i` when `i >= value` |

**Tier A only paints; `applyColors` is what un-paints.** A threshold that stops being met leaves its colour on the segments until the base colour is written again, and only `applyColors` writes it. So `applyThresholdColors` records the count it last painted at in `rows[i].thresholdLit`, and a count below that re-runs `applyColors` (base first, thresholds last) — one pass per drop, none while nothing is painted. The static resources' power-event path (`updateResourceValues`) calls it too; before 2026-09-23 it did not, so Arcane Charges, Holy Power, Chi and Soul Shards changed colour only on a full Refresh and then held it (reported on Arcane: red from 4 charges stuck at 1–3). Pinned by `tests/thresholdclear_check.lua`.

**Tier C reads nothing.** A strip's count is secret and, unlike Tier B, there is no secret *value* to fold — the number only ever exists engine-side inside the aura container. What is knowable is a pip's own index, and the engine shows pip `i` only once stacks reach `i`, so a per-pip colour can gate on "the count reached THIS pip" and on nothing else. Highest matching threshold wins.

**That makes `single` exact and the other two approximations.** Colouring only pip `value` lights at the threshold and never before. `all_previous` and `all` both ask for pips *below* the threshold, which a pip index cannot gate — colouring pip 1 for a threshold of 12 would show the threshold colour at one stack — so they fall back to "from this stack upward", which can never colour a pip the player has not earned. The animated border honours all three exactly, because a border window's reveal is `applications >= value` wherever the window sits; if the recolour is ever wanted to match, the route is the same run geometry drawn as a fill instead of edges (one extra slot per run), not a cleverer per-pip rule.

Two consequences, both permanent:

- **`mode` does not apply.** `all` and `all_previous` both mean "color pips 1..N *because* the count reached `value`", which requires the count. Options hides the distinction (greys the mode dropdown and shows a hint); the Add button stores `"single"` so the field still reads honestly if the entry is ever re-pointed at a Tier A resource.
- **Segmentation must be on.** With `stack_strip_segmented` off, `n` is 1 — one bar spanning the whole cap — so there are no per-pip slices to color and `updateStackPips` leaves the strip on its flat color.

**Scoping: `resource_threshold.resource`.** nil means the primary row; otherwise it is the strip's `base`. nil is also the legacy meaning, so no migration was needed. This field is the actual fix for the reported bug — the threshold list is keyed per *spec* (`getThresholdSpecKey`), so before it existed every entry in a Frost Mage's list was evaluated against whichever row was being drawn, and only the primary had a public count. A threshold meant for the Shatter strip therefore recolored the **Icicles** bar. Tier A and Tier B both skip entries carrying a `resource`; Tier C matches its own `base`, plus nil when the strip *is* the primary (Sweeping Strikes, Teachings, Art of the Glaive on Havoc).

**Rebuilds are consumer-detected, not producer-announced.** Colors are baked into the pip bars at build time, and the build guard only watches `n` and the cap, so a threshold edit would otherwise be invisible until something else forced a rebuild. `stackThresholdSig` folds the strip's thresholds into a cheap allocation-free number that `updateStackPips` diffs against `set.thresholdSig`; a mismatch stamps `set.n = -1` so the existing `ensurePips` rebuild branch runs — which tears the old container down properly, where clearing the `pipSets` entry would strand it shown. The signature is only stamped when a build actually happened, so a pass declined for combat or secrecy still asks for one next tick. Producer-announced invalidation was tried first and dropped: the Options edit buttons call `invalidateThresholdColorCache`, but a **profile switch** fires no threshold callback at all, so that route was already missing a surface (`.context/patterns.md`, "make the consumer detect the change").

**Baked at build time means every OTHER writer must consult the override too.** `applyColors` re-styles the pip bars on every Refresh (`auraTap.stylePips`, so the strip follows a texture or colour change), and it flat-wrote the flat resource colour to all `n` of them — which erased the Tier C colours on the first pass after the build, i.e. before they were ever seen. It now calls `stackThresholdColor` per pip with the same `base` / `isPrimary` / `segmented` inputs the build closure uses, and falls back to the flat colour only where no threshold claims the pip. This is the pip form of the viewer-child alpha rule in `.context/patterns.md`: a shared visual property must not depend on writer order. Both writers now go through one `applyPipColor`, so the next change lands in one place instead of two.

### The animated threshold border (`stack_strip_threshold_glow`, default off)

A pulsing border around the strip, in each threshold's own colour, revealed by the engine at exactly that stack count. `auraTap.ensureBorder` / `layoutBorder` / `setBorderShown`, keyed by the same row-scoped tap key as the pips and torn down by the same `hideStackPips`. It is independent of `stack_strip_segmented` — it spans the whole strip, so it works with segmentation off too — and it carries its own `auraTap.borderSigs[key]` guard rather than riding the pip rebuild.

**Why a bound fill and not a border frame.** An aura slot button is shown on aura PRESENCE — `SetShown(secretwrap(auraData ~= nil))` (`Blizzard_CustomAuraButton.lua:576`) — and `DoesAuraPassCandidateFilters` (`Blizzard_AuraContainerUtil.lua:48`) has **no `applications` field**: the whole filter set is spellIDs, dispel types, `processedAuraType`, `canApplyAura`, `isBossAura`, `isBossOrRoleAura`, `isFromPlayerOrPlayerPet`, `isRoleAura`, `isPriorityAura`, `isStealable`, `maxDuration` and the two nameplate flags. So an ordinary backdrop or texture child, on the slot button or on its own tap, can only ever track whether the aura exists — it would light at one stack and stay lit. `statusBar:SetValue(applications, interpolation)` in `ApplyApplicationBar` (`:338`) is the single thing the engine drives from the protected count, so the cue has to **be** a fill.

**The reveal is `ensurePips`' trick against a wider window.** Each edge is a clip holding a bar `cap` windows long, slid back `(value - 1)` windows, so the fill's leading edge sits at `windowStart + (applications - value + 1) * windowLen`: clear of the window below `value`, exactly covering it at `value`. The formula is position-independent, which is what lets one implementation serve both a whole-bar border and a run of one.

**The border honours `mode`; the segment recolour cannot.** This asymmetry is why `stackThresholdRuns` exists separately from `stackThresholdColor`. A pip's colour can only ever say "the count reached THIS pip", so `all_previous` would light pip 1 in the 12-threshold's colour at one stack — which is why Tier C ignores mode and always runs from the chosen stack upward. A border *window* is not bound that way: its reveal is `applications >= value` wherever the window sits, so the window can be one segment (`single`), the stretch below the threshold (`all_previous`) or the whole bar (`all`) and still light at exactly the right count. The Options mode dropdown is therefore live for strips, and `stackThresholdSig` folds the mode in so a mode-only edit still forces a rebuild.

**Runs never overlap, and that is load-bearing.** One whole-bar overlay per threshold was the first design and it is wrong twice: additive layers *sum* rather than override, and the pulse takes alpha below 1, so a lower layer bleeds through the upper. Runs are instead carved in ascending order against a watermark, so no pairing of modes can overlap — an `all` entry claims the rest of the bar and any threshold above it collapses to nothing and is dropped. Nothing being drawn over anything else is also what makes additive edges safe: the only thing behind one is the bar background.

**A run stops at its own threshold** (except `all`). Running on to the NEXT threshold's boundary was the first cut and it bordered *empty* segments — at 6 of a 6/12 pair the border reached pip 11, outlining five pips the player had not earned. Under `all_previous` the border's lit extent therefore equals the strip's filled extent.

**Geometry:** two long edges per run, plus one short edge capping each end (owned by the first and last run, so the rectangle closes rather than leaving floating lines). The border sits **outside** the bar, offset by its own thickness on every side, rather than covering the first two pixels of fill. `BORDER_THICKNESS` is a fixed 2px — a `ponytail:` simplification, with the upgrade path noted at the constant. Orientation-aware: the long edges are top/bottom on a horizontal strip and left/right on a vertical one, and a cap always fills across the strip's short dimension, so its window length is the cross-length rather than the run's.

**Boundaries follow the segments, not an even division of the strip.** `layoutBars` spaces segments at a pitch of `segLen + gap`, so dividing the strip by `cap` — which the first cut did — puts the border's edges further off with every segment and ends a run mid-segment. `layoutBorder`'s `edgeAt` takes the pitch from the same numbers `layoutStackPips` already has, and distinguishes a leading boundary (the left side of segment *v+1*) from a trailing one (the right side of segment *v*, a gap-width earlier). With `stack_strip_segmented` off there is one continuous bar and no gaps, so it falls back to a fraction of the length. Boundaries are stored in pip units and scaled at layout, so a resize needs no rebuild.

**One animation for the whole border**, an alpha `AnimationGroup` on the container — an addon-owned frame — created once and `Play()`ed, so the engine drives it with no per-frame addon write and nothing to read. An edge still renders only where its fill reaches, so the pulse is invisible until a threshold is actually met.

**Do not** try to reach past this by anchoring a frame onto `bar:GetStatusBarTexture()` to follow the fill — that rect derives from the secret `applications`, and a dependent anchored onto a bound region is the forbidden-aspect shape that has thrown here twice (see the tap-FS layout note above). And recolouring the whole border to "the highest threshold reached" is not available at any price: that is a read of the protected count.

### One table describes all of them

`STACK_STRIPS`, keyed by resource token, is the single source: `base` (tap-key base), `labelKey` (locale key for the Options threshold picker), `auraIDs`, `cap`, `colorKey`, and optionally `unit` / `filter` / `noReadout`. Two rows set `noReadout` — Art of the Glaive and Unbound Flame. Every consumer reads it — `stackPipSpec`, `refreshResourceCount`'s host builder, `releaseRow`, `hideStackPips`, `registerPowerEvents`, `isSecretBackedResource`, `refreshRow`, `updateValueText` and the colour resolver.

**Adding a strip used to mean naming it in nine places, and a miss in any one of them failed silently — differently each time.** Missing from the token chain built no strip at all (the Shatter bug); missing from a teardown list left it drawing over whatever replaced it (the Arcane Salvo bug). Both shipped. One row now feeds all nine, which makes both defects unrepresentable rather than merely tested-for.

Three details are deliberate:

- **`cap` is uniformly a function**, even for the five strips whose answer is a constant. Callers then need no type test on a path that runs hundreds of times a second, and talent- or spec-scaled caps (Sweeping Strikes 12 ⇄ 18, Arcane Salvo 20 ⇄ 25, nearby souls 20/15, Art of the Glaive 6/20) resolve fresh per render with no event of their own.
- **The `auraIDs` maps are inline.** They had been seven file-scope locals read from exactly one place each; folding them in cost one local and freed seven. The main chunk sits at **186/200** as a result, down from 192.
- **Shatter keeps one hand-rolled branch**, in `registerPowerEvents`. It is the only strip bound to a unit other than the player, so it alone needs event registration and teardown (`shatterState`) — behaviour no table field expresses. `tests/stripbases_check.lua` allows exactly that one exception and fails on any other.

`ssState.maxStacks` is gone. It had been mirrored on every render and documented as holding the cap rather than the segment count, but once the consumers read `STACK_STRIPS` its only reader was the line that had just written it — the strip's `cap` calls `getMaxStacks` directly now. Proven unreferenced repo-wide (`libs/` included, and in string-key form) before removal, per the declared-sweep rule in CLAUDE.md.

- **On** — one host segment per stack, the pip tap clipped to a slice per host. 12/18, 4, 20, 15, 20/25 and 20/15 segments respectively.
- **Off** — a single host spanning the row, and the tap bound at the aura's cap so the engine fills the one bar to `stacks / cap`. Continuous fill, same renderer.

**Segment count and cap are two different numbers and both travel.** `stackTap.segmentsFor(cap)` is the single mapping (`cap` while segmented, else 1) and is called from exactly two functions — `stackPipSpec`, which now returns `key, ids, n, cap, unit, filter`, and the six `refreshResourceCount` branches that build the hosts. They have to agree: the hosts and the tap would otherwise be built to different lengths. `updateStackPips` then passes `n` as the pip count and `cap` as `maxApplications`.

**Four of the eight caps are resolved per render, and none owns an event.** Sweeping Strikes flips 12 ⇄ 18 on Improved Sweeping Strikes, Arcane Salvo flips 20 ⇄ 25 on Spellfire Salvo, the nearby Soul Fragments strip is 20 on Havoc and Vengeance and 15 on Devourer, and Art of the Glaive is 6 on Havoc and 20 on Vengeance/Devourer. All three resolve through a helper called fresh on every render — `ssState.getMaxStacks`, `stackTap.arcaneSalvoMax`, `stackTap.nearbySoulsMax`, `stackTap.artOfGlaiveMax` — so nothing caches a stale cap; `talentEventFrame` drives a `Refresh` on `PLAYER_TALENT_UPDATE` **and** `PLAYER_SPECIALIZATION_CHANGED` even when the primary power type is unchanged, and the rebuild guard compares `maxApplications` as well as the segment count, so the pip set is released and rebuilt at the new cap on the first writable pass. A talent- or spec-scaled cap therefore needs **no** event frame of its own.

**No strip caches its cap.** Each `STACK_STRIPS` row resolves it fresh through its `cap` function, so nothing can hold a stale one; Arcane Salvo, the nearby Soul Fragments strip and Art of the Glaive own no state table at all, and their helpers hang off the shared `stackTap` table because the main chunk is near Lua's 200-local ceiling (**186** after the table rework, down from 192).

Nothing outside `ensurePips` needed a branch: `layoutPips` at `set.n == 1` anchors the one bar at offset 0 and sizes it `w × h`, where `layoutBars` has already made `w` the whole row (`barWidth = (frameWidth - totalGap) / activeResourceCount` with `activeResourceCount == 1` and no gaps); `stylePips` and `setPipsShown` iterate or toggle the same set regardless of its length.

The Rogue Coup de Grâce strip is **not** governed by this toggle — it is a separate `ensurePips` consumer under the `"cdg"` key with its own eligibility, and passes no `maxApplications`, so it keeps the default `maxApplications = n`.

The Options toggle calls `component.Refresh()`, not `ReevaluatePowerType()`: the power type does not change, so `ReevaluatePowerType` would early-return. `Refresh` re-runs `refreshResourceCount` (new host count) and `updateStackPips`, whose guard compares both `n` and `maxApplications` and so releases and rebuilds the pip set.

## Arms Warrior — Sweeping Strikes

Opt-in via `arms_sweeping_strikes` toggle; requires the Sweeping Strikes talent (260708). Stack segments: 12 base, 18 with Improved Sweeping Strikes (383155) — or a single continuous fill bar with `stack_strip_segmented` off (see "Stack strips — segmented or continuous"). Each single-target damaging ability consumes a stack and triggers an extra hit.

**Stack source (engine-driven since 2026-08-22):** nothing is read. `updateStackPips` builds an `auraTap.ensurePips` set under the `"sweepingstrikes"` key (row-scoped via `tapKeyForRow`; row 1 keeps the bare string) — one aura slot per rendered segment, each binding its own StatusBar at `maxApplications = <max stacks>` — and the engine fills each bar from the aura's secret `applications`; `layoutStackPips` clips each to its own slice from `layoutBars`. Segmented, the segment count *is* the max stacks and the slices come out one stack wide; unsegmented, there is one slot and one full-width bar at the same max. The numeric readout beside it is a bound FontString on the shared tap container (`auraTap.ensure`, `"sweepingstrikestext"`, pass-through formatter so 0 and 1 render), styled and anchored by `applyStackTapFont` and re-applied via `stackTap.fontDirty` after a blocked fonts pass. The addon-owned `valueText` on that row is hidden once that FS exists, and `updateValueText` returns early for this power type.

This replaced a BuffIcon/BuffBar viewer-child scan (`findSweepingStrikesChild`) that read `applications` through the matched `auraInstanceID`. That call returns nil while auras are secret — for the whole of every pull — so the strip read **0 stacks in combat**, which is the only time it matters. The scan is gone, the `OnUnitAura` hooks with it: Sweeping Strikes registers **no events at all**, `Refresh` converges the build, and `arms_sweeping_strikes` is no longer a `SR_CDM_KEYS_BY_CLASS` keep-alive key. The host segments are blanked (`emptyStackHosts`) so nothing stale shows through when the aura drops and the engine hides the taps.

Threshold colors go the **Tier C** route (see "Threshold colors on stack strips"). `isSecretBackedResource` still includes `SWEEPING_STRIKES_ARMS`, so `applyThresholdColors` still short-circuits at `getCurrentResourceCount() == nil` — but the recolor now happens per-pip at build time instead of not at all. Sweeping Strikes is one of the three strips that can be a *primary*, so it answers to entries with `resource = nil`.

Max stacks resolve at render time, so respeccing Improved Sweeping Strikes flips the count on the next `PLAYER_TALENT_UPDATE → Refresh` — and, because a bound bar can never be re-bound, `ensurePips` releases the whole set and rebuilds it at the new count on the first writable pass. **This is the case that forces `maxApplications` into the rebuild guard.** With segmentation off the segment count stays 1 across the respec while the cap moves 12 ⇄ 18, so a guard that compared only the segment count would never rebuild and the one bar would stay scaled to the old cap for the rest of the session.

## Frost Mage — Shatter (Freezing stacks on the target)

`mage_shatter_stacks` (default off) adds a **second row** on Frost, alongside Icicles rather than replacing them — the first resource in this component to be an extra row rather than a spec's primary. Max **20** stacks of **Freezing** (`1221389`), the debuff the player stacks on the current target and that Shatter consumes — 20 segments, or one bar filled to `stacks / 20` with `stack_strip_segmented` off. `mage_shatter_color` tints it. With `frost_icicles` off the spec has no primary, and Shatter takes row 1 on its own at the primary's `height` (see "Rows"). It is the only extra that can: every other extra's spec has an untoggled primary.

**The count is never read.** Freezing is a secret aura like every other, so the strip is an `auraTap.ensurePips` set bound to the **target** with the `"HARMFUL|PLAYER"` filter — the engine writes the applications into each pip and renders it.

**It does carry a numeric readout**, since 2026-09-08. It used not to, and the reason was never Shatter: the count FontString lived on `auraTap.ensure`'s shared container, which is fixed at `SetUnit("player")` + `"HELPFUL"`, so `updateStackPips` returned before the text tap for any strip whose unit was not the player. The readout now rides **the strip's own pip container** (`ensurePips`' `wantCount` slot), which already has the right unit and filter — and, more importantly, is the same container `shatterState.syncTarget` disables on a friendly target. That is what makes a target-bound readout safe: on a unit the player can assist the identity filter is *skipped*, which admits every aura rather than none, so a second container would have had to replicate that gate exactly and stay in step with it forever. One container, one gate.

**`refreshRow` is what builds it**, through the shared stack-strip branch it takes with Sweeping Strikes, Teachings and Wild Imps (`updateStackPips`). `SHATTER_FREEZING` must be listed in that branch's condition: `updateStackPips` has exactly one call site, so a resource missing from it never calls `ensurePips`, never stamps `shatterState.tapKey`, and therefore never reaches `syncTarget` either — the visible result is a strip of permanently empty host segments and a target watcher that no-ops on its first line.

**A target change must ask the engine to re-parse; the unit token does not move.** `SetUnit` early-outs on an unchanged token (`Blizzard_AuraContainer.lua:40`) and `SetEnabled` on an unchanged flag (`:28`), so a hostile → hostile swap fires nothing at all container-side and the strip held the previous target's stacks until the next `UNIT_AURA` on the new one — live bug, reported 2026-09-16. `shatterState.syncTarget(true)` therefore calls `container:UpdateAllAuras()`, Blizzard's sanctioned external refresh hook, and the watcher also takes `UNIT_FACTION` on `target` and `player` because a reaction flip moves the friendly/hostile gate with no target change at all, and when the player is mind controlled only `"player"` fires. The `refresh` argument exists to keep that off the Refresh path, which calls `syncTarget()` hundreds of times a second in combat. **The threshold border is a second container on the same unit and filter** (`auraTap.ensureBorder`, keyed by the same `tapKey`), so `syncTarget` gives it the same `SetEnabled(hostile)` gate and the same `UpdateAllAuras` on a swap. It shipped without either: on a swap it kept the old target's outline, and on a friendly target its skipped identity filter could light it off any aura. There is still no per-target stack count to carry, adjust or invalidate — which is the whole reason this survives the aura lockdown.

**A friendly target must DISABLE the container, not empty it.** `DoesAuraPassCandidateFilters` applies `includeSpellIDs` only when `AuraContainerUtil.CanApplyIdentityCandidateFilters` passes, and that gate fails for a HARMFUL aura on a unit the player can assist. When it fails the filter is **skipped**, which admits *every* aura rather than none — so an empty spell-ID map is the opposite of an off switch (`.context/api.md`). `shatterState.syncTarget` therefore calls `container:SetEnabled(hostile)`; `ParseAuras` early-returns on a disabled container, which is the only gate-proof off.

**The addon-side `hostile` test must be the engine's predicate, argument for argument.** `Blizzard_AuraContainerUtil.lua:33-38` reads `UnitCanAssist("player", unitToken, canAssistImmune, canAssistUninteractable)` with both locals set to `true`, so `syncTarget` uses `UnitCanAssist("player", "target", true, true)` — not `UnitIsFriend`, and not the two-argument `UnitCanAssist`. The booleans are the point: Blizzard passes them so immune and uninteractable units (vehicles, teleports, cutscenes) still count as assistable, and a mirror that omits them disagrees with the engine on exactly those units. Every pass where the two predicates disagree is a pass where the container stays enabled while the engine skips `includeSpellIDs` — which admits every aura on the target, driving the 20 pips off whatever happens to be up.

**Registration is one watcher, and the whole of its lifecycle is by hand.** `registerPowerEvents` takes an early branch for this resource (the pips are engine-driven) and calls `shatterState.registerEvents()`; `refreshRow` runs that on every pass, so any re-enable re-acquires it. Teardown is the fragile half: `shatterState.eventFrame` is a **dedicated** frame, so the `powerEventFrame:UnregisterAllEvents()` in the transition handlers does not reach it, and `shatterState.unregisterEvents()` has to be named explicitly at all seven teardown sites — `releaseRow` → `hideRowOverlays`, plus the six copies of the shared transition block (`OnDisable`, `ReevaluatePowerType`, and the shapeshift / spec-change / talent / skyriding handlers). The skyriding copy is the odd one out and the easiest to miss: it is the only transition block that does **not** also call `hideStackPips` / `unregisterVitalityEvents` / `unregisterIgnorePainEvents`, so any audit that enumerates the blocks by grepping for one of those three silently skips it. A site that omits it leaves `PLAYER_TARGET_CHANGED` live on an abandoned `AuraContainer` that keeps re-pointing itself and parsing every `UNIT_AURA` engine-side, at no Lua-memory cost — nothing would ever report it.

**`shatterState.tapKey` is stamped on every pass, not on the pass that builds.** `hideRowOverlays` nils `tapKey` on release, but `releaseRow` only calls `auraTap.setPipsShown(key, false)`, which is a bare `container:SetShown(false)` — the set stays in `auraTap.pipSets` at the same `n`. So a release-then-re-add cycle (toggle off/on, row-count change, spec swap out and back) finds the set already valid and skips `ensurePips`' build branch entirely. Stamping only inside that branch would leave `tapKey` nil for the rest of the session, `syncTarget` returning on its first line, and a still-`SetEnabled(true)` container re-shown with no gate at all. `updateStackPips` therefore stamps the key and calls `syncTarget()` after `setPipsShown`, on every pass where the strip's unit is `"target"`. That is safe on the Refresh path: it allocates nothing, and both `SetEnabled` and `SetUnit` short-circuit on an unchanged value (`Blizzard_AuraContainer.lua:28`/`:40`), so the steady-state cost is one `UnitExists` plus one `UnitCanAssist`.

Safe at row ≥ 2 precisely because it needs no *dedicated* per-resource event frame — those still write to row 1.

## Demonology Warlock — Wild Imps

`warlock_wild_imps` (default off) adds a **second row** on Demonology, alongside Soul Shards rather than replacing them — the same extra-row shape as the Frost Mage Shatter strip. >
> **Art of the Glaive can be up alongside the nearby Soul Fragments strip** on every DH spec, and it still **opts out** via `stackTap.noReadout` — checked in `updateStackPips`, and also passed to `ensurePips` as `wantCount` so the slot is never even built. That is now a product choice rather than a workaround: it is a threshold counter whose pips already answer "how close to 6 / 20", and a second number on screen would be noise. `updateValueText` returns early for it too, since the count is secret and there is nothing legal to write.

## Arcane Mage — Arcane Salvo

**The count is never read.** The aura is secret like every other, so the strip is an `auraTap.ensurePips` set bound to the **player** with the default `"HELPFUL"` filter — `stackPipSpec` passes neither a unit nor a filter — and it shares `updateStackPips` / `layoutStackPips` / `emptyStackHosts` with the other four. It registers no events (`registerPowerEvents` takes the shared engine-driven early return); `refreshRow` converges the build. It carries the bound `stackTap` numeric readout with the row's own `valueText` hidden behind it, the same way Wild Imps does, so `updateValueText` returns early for this power type and `isSecretBackedResource` lists it (threshold colors take the **Tier C** per-pip path).

**Always row 2 in practice.** Arcane Charges is the Arcane secondary and is not gated by a toggle, so there is always a primary ahead of it (see "Rows").

> ⚠️ **A strip must be named in `releaseRow` as well as in `hideStackPips` — they cover different paths.** Turning `mage_arcane_salvo_stacks` **off** drops row 2 through `syncRows` → `releaseRow`, which never calls `hideStackPips`. A base missing from `releaseRow`'s list therefore leaves its pip container `SetShown(true)`, still live-anchored to row 2's now-hidden host bars and therefore **still drawn** — WoW anchoring does not auto-hide children. Every *other* teardown path (`OnDisable`, `ReevaluatePowerType`, talent, spec change, shapeshift) goes through `hideStackPips` instead. Arcane Salvo shipped missing that line and it was added; `tests/stripbases_check.lua` now enforces that every base `stackPipSpec` produces is named in both lists, so a future omission fails the suite instead of shipping silently.

## Devastation Evoker — Unbound Flame

`evoker_unbound_flame` (default off) adds a **second row** on Devastation, alongside Essence rather than replacing it — the same extra-row shape as Wild Imps and Arcane Salvo. The row exists only with **all 4 points in Rising Fury**: a Tiered node (`110414`) whose third entry, `1271788` (the 4th point), is the one that turns Dragonrage into Unbound Flame, so `getActiveResourceTypes` gates on `IsPlayerSpell(1271788)`. A respec needs no extra wiring — `PLAYER_TALENT_UPDATE` already drives `Refresh`, which re-derives the rows. Stacks of **Unbound Flame** (`1292323`), the buff Dragonrage leaves behind when it ends: each stack is one cast of the replacement spell, capped at **4** and expiring after 60 seconds. `evoker_unbound_flame_color` tints it, defaulting to Dragonrage's red.

**The strip counts down, not up.** Every other stack strip builds toward a threshold; this one is handed its full 4 and decrements per cast. Nothing in the rendering cares — the engine fills pip `i` while `applications >= i` either way — but it is why Tier C threshold colors read oddly here ("from this stack upward" describes stacks you have *left*).

**No numeric readout**, the second strip after Art of the Glaive to set `noReadout`. Here it is not a collision: the number showed **1 against 4 available casts** in play and was not wanted, so the slot is simply never built. The pips are the readout. Worth keeping in view if the strip is ever revisited — `SetApplicationCount` and `SetApplicationBar` read the *same* engine `applications` value, so a readout of 1 says the pips were likely showing one filled segment of four as well, i.e. `1292323` may not stack the way `CumulativeAura = 4` suggests.

> ⚠️ **The aura is `1292323`, not the `1292321` the spell is usually cited by.** Four spells are named Unbound Flame. `1292321`, `1292322` and `1292325` are the castable versions — no `SpellAuraOptions` row at all, so not stacking auras, and `1292321` has `DurationIndex 0`. Only `1292323` carries `CumulativeAura = 4` and the 60s duration, and its buff text is the one that reads "Dragonrage changed to Unbound Flame. Unbound Flame may be cast 1 more time." Filtering on the cast id would have produced a permanently empty strip with nothing to debug.

**Always row 2 in practice.** Essence is the Evoker class secondary (`classSecondaryPower.EVOKER`) with no toggle in front of it, so there is always a primary ahead of it on Devastation (see "Rows").

**The duration cue is the expiry border, `evoker_unbound_flame_expiry` (default off), and it is expected not to fire.** A "15 seconds left" threshold is not computable — the aura is secret, so remaining time cannot be read at all. `AddPandemicRegion` is the only engine-driven "running out" cue that survives secrecy, so `applyUnboundFlameExpiry` registers a border host on a dedicated tap (`auraTap.ensurePandemic`, the `ensureGlow` shape with the engine driving the shown state instead of aura presence). But Blizzard derives the window from `GetRefreshExtendedDuration − GetAuraBaseDuration`, and Unbound Flame is applied once when Dragonrage ends and never refreshed, so that difference should be **0** and no window should ever open. Shipped opt-in and off precisely because the prediction is untested: if the border never appears in play, the setting is the evidence and the whole cue can come out. See `.context/patterns-auracontainer.md` "Pandemic regions".

It targets `rowFrame` rather than `resourcesFrame` — the Lock and Load glow tap sits on a primary and can span the component, an extra row cannot. Devastation's primary is Essence with no toggle in front of it, so the strip is always row 2 and `rowFrames[2]` is pooled by index, which keeps the cached container's anchor valid across row-count changes.

## Paladin — Crusading Strikes swing timer

Opt-in via `paladin_swing_timer` toggle; requires Crusading Strikes talent (404542). Detects auto-attack swings via `UNIT_SPELLCAST_SUCCEEDED` with spell ID 408385. Gradually fills the next depleted Holy Power segment in a lighter class color over the swing duration.

**Period:** deterministic — `cachedMainhandSpeed × CRUSADING_STRIKES_PERIOD_FACTOR (1 / 1.15, i.e. the 15% attack-speed *increase* the talent grants as of 12.1 — it was a 20% slowdown before) / (hasteMult × zealotsFervorMult)` — where `zealotsFervorMult` is `1 + bonus` for the active Zealot's Fervor rank (`SRC.ZEALOTS_FERVOR_BONUS = { [1] = 0.20, [2] = 0.40 }`, TraitEntryID 115165), resolved via the same `C_ClassTalents.GetActiveConfigID` + `C_Traits.GetNodeInfo` walk as Innate Magic and cached on `private.swingZealotsFervorMult` for cheap per-frame reads (refreshed at `swingState.registerEvents` time, which `PLAYER_TALENT_UPDATE → Refresh` re-runs on respec). Zealot's Fervor is a melee-only attack-speed bucket that doesn't appear in spell haste, so without this multiplier the predicted period runs 20%/40% too long for rank 1/2 talented players and the bar visibly stutters as it resets to 0 each real swing while only partway filled.

**Mainhand speed:** `cachedMainhandSpeed` is parsed from the mainhand tooltip via `C_TooltipInfo.GetInventoryItem("player", INVSLOT_MAINHAND)` at register and refreshed on `PLAYER_EQUIPMENT_CHANGED` (mainhand) and `PLAYER_ENTERING_WORLD` (covers reload-mid-combat / mid-M+ where tooltip data may not yet be populated at register time). The scan walks every tooltip line and accepts the first `(%d+)[%.,](%d+)` decimal in [0.5, 4.0] from `rightText`, so it's localization-independent for both the "Speed" label (never keyed on) and the decimal separator (period for enUS / zh\*, comma for most European locales — captured halves are spliced with a period before `tonumber`, which itself only accepts period-decimals). A failed parse preserves the prior cached value. `unregisterEvents` clears the cache, so a zone-in that unregisters and re-registers after `PLAYER_ENTERING_WORLD` with the tooltip still empty would leave no speed and no event to retry — the `UNIT_SPELLCAST_SUCCEEDED` handler therefore re-reads the tooltip on any swing that finds the cache nil (live report: timer dead for a whole M+ run until toggled). Tooltip data is non-secret intrinsic item data, so the read works through combat where `UnitAttackSpeed` would return secret; in 12.0+ each line is auto-surfaced (`leftText` / `rightText` are direct fields on the line table, no `TooltipUtil.SurfaceArgs` step — that helper is no longer present in this client).

Haste sampled from Redemption's cast time (spellID 7328, non-secret). Out-of-range delays cannot poison the period; weapon swaps update on the same frame as the equip with no convergence period. Timer resets on each swing; HP gains from other abilities reposition the fill to the new next segment without resetting the timer.

## Resource threshold colors

Per-spec recoloring of discrete segments when the current count reaches a configured value. Stored at `profile.components.SecondaryResources.resource_thresholds` keyed by `"CLASSFILENAME-specIndex"`; each entry has `{value, color, mode}` where mode is `single` (color segment N only), `all_previous` (color 1..N), or `all` (color 1..current). Multiple thresholds per spec are processed ascending so higher values overwrite lower ones on overlap.

**Two tiers:**
- Public-count resources (UnitPower, runes, and all `GetPlayerAuraBySpellID + diff-cache` counts — MW, WW, ToTS, icicles, vengeance fragments, etc.) support all three modes via direct integer comparison.
- `SpellChargeInfo.currentCharges`-backed resources (Fire Blast, Aimed Shot) and Vengeance Soul Fragments are secret-backed and fall back to an `EvaluateColorFromBoolean` fold that only honors the `all` mode — the Options UI locks the mode dropdown to `all` for those resources.

Generic thresholds run after the existing `enhancement_mw_threshold` highlight, so user-configured entries win on any overlapping MW segments.

## Devourer Demon Hunter — Reap forecast

Opt-in via `devourer_reap_forecast` toggle, gated to `playerPowerType == SOUL_FRAG_DEVOURER` so the overlays don't bleed onto Vengeance / other power types that share `resourceFrames[1]` as their host.

**`reapFc` is row 1's, and all three per-row writers say so.** Devourer is a *primary* resource — `SRC.SOUL_FRAG_DEVOURER` appears only in `SRC.specSecondaryPower` — and extras append after the primary, so the Devourer bar is always row 1. `refreshResourceCount`'s opening `reapFc.hideAll()`, `updateValueText`'s tap-FS pre-block and `refreshRow`'s fonts pass are each guarded on `rowIndex == 1` accordingly; without that, any second row (the nearby Soul Fragments strip is the first one that can exist on this spec) hid the overlays after row 1 had just shown them and flip-flopped the text seam every pass. Full rationale under "Rows — how one component drives several resources". The seam's bound half now anchors to `rowFrame` rather than `resourcesFrame` for the same reason.

Overlays the existing soul bar with three elements:

1. **Reap-consumption preview** anchored to the soul bar's fill-texture right edge (width = `reapCap / cachedDevourerMax * barWidth`, pure non-secret arithmetic; tracks the current soul fill via the StatusBar fill seam), parented to a `SetClipsChildren(true)` clip frame (`reapFc.clipFrame`) sized to the bar so the slab is masked when the fill seam is near the right edge — reading `fillTex:GetWidth()` to clamp the slab in Lua taints (the texture width is set internally from the secret `cachedDevourerSouls`), so the clip frame replaces the arithmetic clamp with a render-time clip.
2. **Souls-nearby meter** — ReapMeter's `sfBar` analog, inside the clip frame. An **engine-driven bound StatusBar** instead — `reapFc.ensureTapAmmo()` creates a dedicated aura-tap container (`auraTap.ensureBar`, slot `"reapammo"`) parented to `reapFc.ammoClip`; Blizzard drives `SetMinMaxValues(0, maxApplications)` + `SetValue(secret applications)` via `SetApplicationBar`, the slot button self-hides while no SF aura is active, and `reapFc.updateTapAmmo` owns geometry only. No CDM tracking needed — the slot matches the aura by spell ID directly.

   **The cap is applied by a scissor, not by the bind.** The button carries `DenyTaintedAccessWhenAurasAreSecret`, so its width and the bound `maxApplications` are writable only out of combat — but the cap flips on the Reap → Eradicate override, which only ever happens *in* combat. A cap-scaled bind therefore could never converge while it mattered: the preview slab (a plain Texture, freely resizable) grew to the 10-cap width while the ammo bar stayed at its 4-cap scale, so the extended Eradicate range never filled (live-reported 2026-08-29). The button is instead a **fixed `reapFc.capMax` (10) souls long**, set once and never rewritten, and `reapFc.ammoClip` — an addon-owned `SetClipsChildren` frame nested inside the main clip frame — is trimmed to the live cap width every pass. Fill is `applications / capMax` of a capMax-wide button, i.e. exactly one soul-width per application at any cap, and the scissor hides whatever Reap could not consume. Both clip frames' anchors track the fill seam, so nothing per-frame is read back.

   The button's width also bakes the soul→pixel scale (`barWidth / cachedDevourerMax`), and **both inputs can move while the button is unwritable**: the soul max is 50, 35 with Soul Glutton, and **40 in Void Metamorphosis** — a mid-pull change, which left the tail of the extended slab unable to fill. `reapFc.ammoBaked` records the width the button was last sized to and `ammoClip:SetScale(fullWidthPx / ammoBaked)` carries the correction (a plain addon frame, so `SetScale` is combat-legal); the clip divides the scale back out of its own width to stay in screen pixels, and the next writable pass re-bakes the button and collapses the scale to 1. The legacy CPU-driven `reapFc.ammo` StatusBar is **deleted** — it went with the pre-12.1 fallback whose branches were its only writers.

   **All three forecast colour settings drive live regions**, and `reapFc.applyColors` is the single writer: `devourer_reap_preview_color` → the slab Texture, `devourer_reap_ammo_color` → the **bound** ammo StatusBar (out of combat only, `DenyTaintedAccessWhenAurasAreSecret`), `devourer_reap_pip_color` → `reapFc.pipCS`. The latter two once sat behind a `>= 120100` gate in Options that hid their pickers on every shipping client, on the theory that 12.1 had blocked what they colour; it had not. Deleting that gate as dead also deleted `applyColors`' shared `local ac`, which the still-live bound-bar branch read — a nil global index on every refresh, and the reason both pickers are back.
3. **Collapsing Star breakpoint pip** (`reapFc.pipCS`) at 30 souls, positioned by `pipCSThreshold / cachedDevourerMax * barWidth`, shown only while the Void Metamorphosis aura (`1217607`) is active and auto-hidden when the threshold equals or exceeds the current cap.

   The VM read is **live** — `C_UnitAuras.GetPlayerAuraBySpellID(1217607)` returns data while auras are secret (see `.context/api.md` "Aura rules"). It was hard-gated off on the opposite assumption, which would equally have made `getDevourerSoulMax`'s 40-cap branch dead code; the ammo bar's scale shift on entering meta proves that branch is live. The gate fails closed anyway: a nil read hides the pip.

   **Known:** the pip is a texture on `clipFrame`, so `ammoClip` — a child frame — draws over it. The slab starts at the fill seam and is `cap` souls wide, so it overlaps the pip as souls approach 30. Fixing it needs the pip on its own frame above `ammoClip`; not done.

**Reap cap:** 4 base, 10 with Moment of Craving, detected from the Reap → Eradicate spell override (`C_Spell.GetOverrideSpell(1226019) == 1225826`). Application is picked up via `SPELLS_CHANGED`; the revert is owned by a 0.25 s `C_Timer.NewTicker` (`reapFc.capPoll`), started whenever the cap reads 10 and cancelled otherwise.

There is **no MoC configuration requirement any more.** This used to prefer the BuffIcon CDM viewer's MoC slot, whose non-secret `auraInstanceID` flipped off the moment the aura expired — accurate, but it required the player to add Moment of Craving to Blizzard's CooldownSettings → Buffs → Tracked BUFFS, and it pinned the CDM keep-alive bridge on for *every* Demon Hunter running the forecast. Both are gone (parity item K6).

> **The expected inaccuracy does not exist.** The concern was that the override reverts on Eradicate *consumption* only, so a MoC that timed out unspent would leave the cap reading 10 and the slab 10 souls wide until the next Eradicate — genuinely unfixable, since the poll re-reads the same override and no aura read can settle it either: spell 1238488 is flagged `Passive spell` + `Aura is hidden` and does **not** carry "aura never secret", so `GetPlayerAuraBySpellID` returns nil for it precisely when it matters (`.context/api.md` "Aura rules"). **MoC carries no duration** (live 2026-08-30), so there is no unspent-expiry case at all — consumption is the only exit, which is exactly the edge `capPoll` owns, and the fall-back was verified in play. Freeing the class from the bridge cost nothing.

Separate `devourer_reap_forecast_show_text` toggle (default on, independent of the global Show Value setting) overrides the soul bar's value text with `current (nearby)` — both numbers piped straight into `SetFormattedText("%d")` with no arithmetic, so the secret soul count and secret SF stack count are displayable without taint. 12.1: the exact `%d (%d)` instance-ID path is pre-12.1-only; on 12.1 our text is the bare soul count and the nearby count is rendered beside it by Blizzard via the bound `reapFc.tapStacks` FontString (display-only composition, see "12.1 aura lockdown" — no brackets for now). The `(N)` suffix is gated on the non-secret CDM-child IID presence either way. **The pre-12.1 ammo bar and the `(nearby)` text suffix both require Soul Fragments (1245577) to be added to Blizzard's CooldownSettings → Buffs → Tracked BUFFS** — the SF aura is secret, so its applications is only reachable via the non-secret `auraInstanceID` exposed on the CDM BuffIcon child. Without that config, the pre-12.1 ammo bar stays hidden and the text falls back to the bare soul count. The 12.1 bound ammo bar is exempt: its aura slot matches the SF spell IDs directly, no CDM config involved.

## Warlock — Soul Shard fragments

`warlock_shard_fragments` toggle (default off, child of Show Value). When on and
the player is Destruction, the centered value text shows the fractional shard
count (`%.1f`, e.g. `3.6`) instead of the floored whole count. Demonology and
Affliction always show whole shards regardless of the toggle. The bar fill
already renders the fractional value for Destruction independently.

## Builder prediction

`builder_prediction` toggle (default on). During a cast-time builder, an overlay
bar in `builder_prediction_color` previews the incoming resource on the segments
it will fill. There is no API for generation amounts, so the spell → amount map
is hardcoded per spec in `buildPred.populate` (amounts in fragments for Soul
Shards, whole units otherwise): Destruction — Incinerate (2), Soul Fire (10);
Demonology — Shadow Bolt (10), Demonbolt (20); Arcane — Arcane Blast (1).
Instant builders (Conflagrate, Channel Demonfire) cannot be previewed — the
overlay is driven by `UNIT_SPELLCAST_START` / `CHANNEL_START` and cleared on
every stop/success/fail.
